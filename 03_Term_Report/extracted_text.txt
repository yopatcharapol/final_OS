Line 175: 1. เธรดระดับผู้ใช้ (User-Level Threads: ULT):

Line 177:  ข้อดีเด่นชัด:* มีความรวดเร็วในการสร้าง ทำลาย และสลับบริบทอย่างยิ่งยวด (Zero System Call Overhead) การสลับเธรดเกิดขึ้นผ่านการสลับรีจิสเตอร์ใน User Space โดยไม่ต้องส่งสัญญาณแทร็ปข้ามไปยัง Ring 0 ทำให้สลับเธรดได้เร็วกว่าเคอร์เนลนับสิบเท่า นอกจากนี้ยังสามารถปรับแต่งนโยบายการจัดตารางเวลาได้เองอย่างยืดหยุ่นโดยไม่ต้องขอสิทธิ์ Root [Anderson et al., 1992]

Line 178:  ข้อจำกัดร้ายแรง: ข้อเสียใหญ่หลวงคือ "ปัญหาการบล็อกทั้งโพรเซส" (Blocking System Call Issue) หากมี User Thread ตัวใดตัวหนึ่งเรียกคำสั่งซิสเต็มคอลแบบบล็อกกิ้ง (เช่น การอ่านไฟล์จากดิสก์) เคอร์เนลซึ่งมองเห็นทั้งโพรเซสเป็นหน่วยเดียว จะทำการย้ายทั้งโพรเซสไปอยู่ในสถานะ Blocked ทันที ส่งผลให้เธรดที่เหลือทั้งหมดในโปรแกรมต้องหยุดชะงักตามไปด้วย และข้อจำกัดที่สองคือ ไม่สามารถรันขนานกันบนซีพียูหลายคอร์ได้จริง (No Multi-core Parallelism)* เนื่องจากเคอร์เนลจัดสรรเวลาให้โพรเซสนั้นบนคอร์เพียงคอร์เดียวในแต่ละช่วงเวลา [Tanenbaum & Bos, 2014]

Line 179: 2. เธรดระดับเคอร์เนล (Kernel-Level Threads: KLT):

Line 180: ในโมเดลนี้ เคอร์เนลเป็นผู้สร้าง บริหารจัดการ และจัดตารางเวลาให้กับเธรดโดยตรง ทุกเธรดจะมีโครงสร้าง TCB อยู่ในเคอร์เนลสเปซ และถูกรับรู้โดยตัวจัดตารางเวลาของระบบปฏิบัติการ [Love, 2010]

Line 181:  ข้อดีเด่นชัด:* รองรับการประมวลผลบนซีพียูหลายคอร์ได้อย่างสมบูรณ์แบบ (True Multi-core Parallelism) เคอร์เนลสามารถส่งเธรดต่าง ๆ ของโพรเซสเดียวกันไปรันบนคอร์ที่ 1, 2, 3 พร้อมกันได้อย่างแท้จริง และหากเธรดหนึ่งเรียกคำสั่ง Blocking I/O เคอร์เนลจะสั่งบล็อกเฉพาะเธรดนั้น แล้วสลับเธรดอื่นในโพรเซสเดียวกันขึ้นมาประมวลผลแทนได้อย่างราบรื่น [Silberschatz et al., 2018]

Line 183: 3.2 แบบจำลองการจับคู่เธรด (Thread Mapping Models)

Line 184: จากความแตกต่างระหว่าง ULT และ KLT นักออกแบบระบบปฏิบัติการจึงได้คิดค้นแบบจำลองในการจับคู่ความสัมพันธ์ระหว่าง "เธรดระดับผู้ใช้" (User Threads) และ "เธรดระดับเคอร์เนล" (Kernel Threads) ซึ่งจำแนกออกได้เป็น 3 รูปแบบหลัก ดังนี้ [Silberschatz et al., 2018]:

Line 185: 1. แบบจำลองหลายเธรดผู้ใช้ต่อหนึ่งเธรดเคอร์เนล (Many-to-One Model: M:1)

Line 186: โครงสร้างของแบบจำลองนี้กำหนดให้เธรดระดับผู้ใช้ (User-Level Threads) จำนวนหลายตัวถูกจับคู่ลงบนเธรดระดับเคอร์เนล (Kernel-Level Thread) เพียงตัวเดียว โดยการจัดการเธรดทั้งหมดดำเนินการผ่านไลบรารีใน User Space ดังแสดงในรูปที่ 3.1 [Silberschatz et al., 2018]

Line 190: ในอดีต โมเดลนี้ได้รับความนิยมสูงในระบบที่ไม่รองรับเธรดในระดับเคอร์เนล เช่น Solaris Green Threads หรือระบบปฏิบัติการยุคแรกของ Java ข้อดีคือมีประสิทธิภาพในการสลับเธรดสูงมากและใช้หน่วยความจำน้อย แต่ข้อจำกัดเรื่องการบล็อกทั้งระบบเมื่อมี 1 เธรดรอ I/O และความไร้ความสามารถในการกระจายงานลงบน Multi-Core ส่งผลให้โมเดลนี้ไม่ถูกนำมาใช้เป็นสถาปัตยกรรมหลักของระบบปฏิบัติการสมัยใหม่อีกต่อไป [Silberschatz et al., 2018]

Line 191: 2. แบบจำลองหนึ่งเธรดผู้ใช้ต่อหนึ่งเธรดเคอร์เนล (One-to-One Model: 1:1)

Line 192: โครงสร้างของแบบจำลองนี้กำหนดให้ทุกการสร้างเธรดระดับผู้ใช้ 1 ตัว จะมีเธรดระดับเคอร์เนลถูกสร้างขึ้นมารองรับโดยตรง 1 ตัวเสมอ การสร้างเธรดผ่านคำสั่งเช่น pthread_create() จะส่งสัญญาณ System Call ให้เคอร์เนลจัดสรรโครงสร้าง TCB และ Kernel Execution Context ขึ้นมารองรับ ดังแสดงในรูปที่ 3.2 [Silberschatz et al., 2018]

Line 197: โมเดล 1:1 ทำให้การ blocking ของเธรดหนึ่งไม่จำเป็นต้องหยุดเธรดอื่น และเปิดโอกาสให้หลายเธรดรันบนหลาย logical processors อย่างไรก็ดี lock dependencies และทรัพยากรร่วมยังอาจจำกัด concurrency และ parallelism ได้

Line 198:  ข้อจำกัดและข้อควรระวัง: ปัญหาหลักคือการสร้างเธรดในโมเดลนี้มีราคาแพง การสร้างเธรดผู้ใช้หลักหมื่นหรือหลักแสนตัวจะส่งผลให้เคอร์เนลต้องแบกรับภาระโครงสร้าง TCB และพื้นที่ Stack มหาศาลจนหน่วยความจำหมดลง (Resource Exhaustion) ดังนั้น สถาปัตยกรรมที่ใช้โมเดล 1:1 จึงจำเป็นต้องพึ่งพากลไก Thread Pools* เพื่อจำกัดจำนวนการสร้างเธรด [Silberschatz et al., 2018]

Line 199: 3. แบบจำลองหลายเธรดผู้ใช้ต่อหลายเธรดเคอร์เนล (Many-to-Many Model: M:N) และ Two-Level Model

Line 200: เพื่อลดข้อจำกัดของแบบจำลอง Many-to-One และ One-to-One แบบจำลอง Many-to-Many อนุญาตให้สร้างเธรดระดับผู้ใช้จำนวนมาก (M ตัว) และมัลติเพล็กซ์ลงบนกลุ่มของเธรดระดับเคอร์เนลที่มีจำนวนเหมาะสม (N ตัว โดย M ≫ N) ดังแสดงในรูปที่ 3.3 [Anderson et al., 1992]

Line 245: > “การเพิ่มจำนวนเธรดและจำนวนคอร์ซีพียู จะทำให้ระบบทำงานเร็วขึ้นเป็นเส้นตรงตามสัดส่วนของฮาร์ดแวร์จริงหรือไม่?”

Line 246: ในทางสถาปัตยกรรมคอมพิวเตอร์ คำตอบคือ "ไม่จริง" การประมวลผลแบบขนานบนฮาร์ดแวร์จริงต้องเผชิญหน้ากับกฎขีดจำกัดความเร็วทางคณิตศาสตร์ (Amdahl's Law, Gustafson's Law และ Universal Scalability Law) รวมถึงข้อจำกัดเชิงกายภาพของลำดับชั้นแคช (Cache Coherence Invalidation) และปัญหาการแชร์ข้อมูลที่ซ่อนอยู่ (False Sharing) ประเด็นเหล่านี้จะได้รับการพิสูจน์และวิเคราะห์อย่างละเอียดใน บทที่ 4: เธรดกับสถาปัตยกรรมฮาร์ดแวร์และทฤษฎีความเร็ว ต่อไป

Line 247: บทที่ 4: เธรดกับสถาปัตยกรรมฮาร์ดแวร์และทฤษฎีความเร็ว (Hardware Architecture & Scalability Laws)

Line 252: คือการออกแบบโครงสร้างของโปรแกรมที่สามารถแยกงานออกเป็นหน่วยย่อยๆ ที่ทำงานเป็นอิสระต่อกัน และสามารถก้าวหน้าไปร่วมกันได้ในกรอบเวลาเดียวกัน ระบบที่ทำงานแบบ Concurrency สามารถทำงานได้บนซีพียูที่มี เพียง 1 คอร์ทางกายภาพ (Single-Core Processor) โดยอาศัยกลไกการสลับเวลา (Time-slicing / Interleaving) เธรดต่างๆ จะสลับกันเข้ายึดครองซีพียูคนละไม่กี่มิลลิวินาที ทำให้ผู้ใช้มองเห็นเสมือนว่าทุกงานกำลังทำงานพร้อมกัน แต่ในความเป็นจริง ในระดับเสี้ยววินาทีหนึ่งๆ มีคำสั่งถูกประมวลผลบนฮาร์ดแวร์เพียงคำสั่งเดียวเท่านั้น [Silberschatz et al., 2018]
