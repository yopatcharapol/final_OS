ใบงานที่ 7-8 (การบ้านประจำสัปดาห์)
บทที่ 7-8 การจัดการหน่วยความจำ และหน่วยความจำเสมือน
รายวิชา ระบบปฏิบัติการ (Operating Systems) — หลักสูตรวิศวกรรมคอมพิวเตอร์ UP
คำชี้แจง:
• การบ้านนี้ครอบคลุมเนื้อหาบทที่ 7-8 ทั้งหมด
• ส่งโดยตั้งชื่อไฟล์เป็นรหัสนิสิต เช่น 67021398_บีม.docx (ส่งเป็นไฟล์ word)
• เขียนตอบด้วยภาษาของตนเอง อธิบายละเอียด แสดงวิธีทำทุกขั้นตอนอย่างครบถ้วน
ตอนที่ 1 คำถามทบทวนความรู้และการวิเคราะห์ (3 ข้อ ข้อละ 10 คะแนน รวม 30 คะแนน)
ข้อ 1. ลำดับชั้นหน่วยความจำและการเชื่อมโยงตำแหน่ง (10 คะแนน)
1.1 จงอธิบายหน่วยความจำทั้ง 3 ระดับ (หน่วยความจำภายใน หน่วยความจำหลัก และหน่วยความจำสำรอง) โดยเปรียบเทียบในด้านความเร็ว ความจุ ต้นทุน และความคงทนของข้อมูล พร้อมอธิบายว่าเหตุใดระบบคอมพิวเตอร์จึงต้องออกแบบหน่วยความจำเป็นลำดับชั้นแทนการใช้หน่วยความจำชนิดเดียว
ตอบ: เปรียบเทียบหมวดหมู่หน่วยความจำ 3 ระดับแบบเนื้อๆ:
• หน่วยความจำภายใน (Internal / Registers / Cache): เร็วสุดยอดระดับสัญญาณนาฬิกา (เสี้ยวนาโนวินาที) แต่ความจุจิ๋วสุด (KB ถึง MB) ต้นทุนต่อบิตแพงสุด และดับไฟแล้วข้อมูลหายเกลี้ยง (Volatile)
• หน่วยความจำหลัก (Main Memory / RAM): ความเร็วปานกลาง (~50-100 ns) ความจุปานกลางระดับกิกะไบต์ (GB) ราคาจับต้องได้ ดับไฟแล้วข้อมูลหาย (Volatile)
• หน่วยความจำสำรอง (Secondary Storage / SSD, HDD): ช้าสุด (ระดับ microsecond ถึง millisecond) แต่ความจุสะใจระดับเทราไบต์ (TB) ราคาต่อบิตถูกสุด และไฟดับข้อมูลไม่หาย (Non-volatile)

ทำไมต้องออกแบบเป็นลำดับชั้นแทนที่จะใช้ชนิดเดียว:
ถ้าเอาแรมเร็วเท่ารีจิสเตอร์ทั้งเครื่องคงจนล้มละลาย แต่ถ้าเอาฮาร์ดดิสก์มาทำแรมเครื่องก็ช้าเป็นเต่า การทำเป็นลำดับชั้นอาศัยหลัก Locality of Reference (ดึงของที่ใช้บ่อยมาไว้ใกล้ตัว) ทำให้ระบบได้ความเร็วเฉลี่ยระดับแคช แต่ได้ความจุและราคาประหยัดเหมือนฮาร์ดดิสก์ เหมือนมีตู้เย็นในห้องนอน (แคช) + ร้านสะดวกซื้อหน้าปากซอย (แรม) + โกดังส่งของต่างจังหวัด (ดิสก์) นั่นแหละเนาะ
1.2 การเชื่อมโยงตำแหน่ง (Address Binding) เกิดขึ้นได้ 3 ช่วงเวลา คือ เวลาแปลโปรแกรม เวลาโหลดโปรแกรม และเวลาดำเนินการ จงเปรียบเทียบทั้งสามช่วงในด้านความยืดหยุ่นในการย้ายตำแหน่ง (relocation) และระบุว่าช่วงใดจำเป็นต้องใช้ฮาร์ดแวร์ MMU ช่วย เพราะเหตุใด
ตอบ: เปรียบเทียบความยืดหยุ่น 3 ช่วงเวลา:
1. เวลาแปลโปรแกรม (Compile Time): ล็อกตำแหน่งจริงตายตัว (Absolute Address) ตั้งแต่คอมไพล์ ย้ายที่ไม่ได้เลย ยืดหยุ่นแย่สุด ถ้าแรมตรงนั้นไม่ว่างต้องคอมไพล์ใหม่
2. เวลาโหลดโปรแกรม (Load Time): คอมไพล์เป็น Relocatable Code แล้วมาผูกตำแหน่งจริงตอนโหลดเข้าแรม ถ้าโหลดแล้วย้ายที่ตอนรันไม่ได้ ต้องปิดแล้วโหลดใหม่
3. เวลาดำเนินการ (Execution / Run Time): ยืดหยุ่นสูงสุด ผูกตำแหน่งตอนคำสั่งจะทำงานจริงๆ ย้ายโพรเซสไปมาในแรมได้ตลอดเวลา

ช่วงที่ต้องใช้ฮาร์ดแวร์ MMU: 'เวลาดำเนินการ (Execution Time)'
เหตุผล: เพราะตำแหน่งจริงในแรมเปลี่ยนไปมาตลอดเวลา ซีพียูยิง Logical Address ออกมา ฮาร์ดแวร์ MMU (มี Base Register) ต้องช่วยเอาไปบวกหา Physical Address แบบเรียลไทม์ระดับเสี้ยววินาที ถ้าให้ซอฟต์แวร์มานั่งบวกเองเครื่องคงช้าจนค้าง
1.3 ระบบหนึ่งใช้การจัดสรรแบบขนาดคงที่ โดยมี relocation register (base) = 24,600 และ limit register = 2,048 จงคำนวณและตอบคำถามต่อไปนี้
ก) ตำแหน่งทางตรรกะ 1,750 จะถูกแปลงเป็นตำแหน่งทางกายภาพใด
ข) ตำแหน่งทางตรรกะ 2,300 จะเกิดเหตุการณ์ใดขึ้น เพราะเหตุใด
ค) โพรเซสนี้สามารถเข้าถึงตำแหน่งกายภาพได้ในช่วงใดถึงช่วงใด
ตอบ: ก) ตำแหน่งตรรกะ 1,750: ตรวจสอบ 1,750 < 2,048 (ผ่าน) -> ตำแหน่งกายภาพ = 24,600 + 1,750 = 26,350
ข) ตำแหน่งตรรกะ 2,300: ตรวจสอบ 2,300 < 2,048 (ไม่ผ่าน! เกิน Limit) -> เกิด Trap / Addressing Error (Segmentation Fault) ระบบปฏิบัติการจะตัดตอนทันที เพราะโพรเซสพยายามแอบอ่านเมมโมรีนอกอาณาเขตตัวเอง
ค) ช่วงตำแหน่งกายภาพที่เข้าถึงได้: ตั้งแต่ 24,600 ถึง (24,600 + 2,048 - 1) คือช่วง 24,600 ถึง 26,647 (รวม 2,048 ไบต์)
1.4 จงเปรียบเทียบเทคนิค Overlay, Dynamic Loading และ Dynamic Linking ในด้านผู้รับผิดชอบ (โปรแกรมเมอร์หรือระบบปฏิบัติการ) ช่วงเวลาที่เกิดการโหลด และประโยชน์ที่ได้รับ พร้อมยกตัวอย่างการใช้งานจริงของ Shared Library
ตอบ: เปรียบเทียบ 3 เทคนิค:
• Overlay: โปรแกรมเมอร์รับผิดชอบ 100% เขียนโค้ดสลับโมดูลเข้าออกแรมเองตั้งแต่ยุคโบราณที่แรมมีน้อยจัดๆ
• Dynamic Loading: โหลดรูทีน/ฟังก์ชันเข้าแรมเฉพาะตอนถูกเรียกใช้งาน (Load on call) ช่วยไม่ให้เปลืองแรมกับฟังก์ชันที่ไม่ค่อยได้ใช้ เช่น ตัวจัดการ Error โดยโปรแกรมเมอร์ออกแบบและ OS ช่วยโหลด
• Dynamic Linking: รวมโค้ดไลบรารี (.dll / .so) ตอนรันไทม์ โดยใช้ Stub ชี้ไปที่ Shared Library ในแรม OS เป็นคนจัดการ ประโยชน์คือหลายโปรแกรมแชร์โค้ดก้อนเดียวกันในแรมได้ ไม่ต้องก๊อปปี้ไปฝังในไฟล์ .exe ทุกตัว

ตัวอย่างการใช้งานจริงของ Shared Library:
เช่น libc.so ใน Linux หรือ kernel32.dll / user32.dll ใน Windows ซึ่งโปรแกรมแทบทุกตัวในเครื่องต้องเรียกใช้ฟังก์ชันมาตรฐานพวกนี้ ระบบโหลดโค้ดไว้ในแรมเพียงก้อนเดียว แล้วให้ทุกโปรแกรมแชร์ใช้ร่วมกัน ประหยัดเนื้อที่แรมมหาศาล
ข้อ 2. การสูญเสียพื้นที่ย่อยภายในและภายนอก (10 คะแนน)
2.1 จงอธิบายความแตกต่างระหว่าง Internal Fragmentation และ External Fragmentation พร้อมระบุว่าการจัดสรรแบบใดทำให้เกิดปัญหาแต่ละแบบ
ตอบ: ความแตกต่าง:
• Internal Fragmentation: พื้นที่เหลือทิ้ง 'ข้างในห้อง' ที่จัดสรรให้ เช่น ให้ห้องขนาด 64 KB แต่โปรแกรมใช้แค่ 40 KB เศษที่เหลือ 24 KB คาอยู่ในห้อง คนอื่นใช้ไม่ได้ เกิดกับการแบ่งแบบขนาดคงที่ (Fixed Partitioning, Paging)
• External Fragmentation: พื้นที่ว่างรวมทั้งระบบมีเยอะพอ แต่แตกเป็น 'เศษเล็กเศษน้อยกระจัดกระจายข้างนอก' จนต่อกันเป็นผืนใหญ่ไม่พอให้โพรเซสใหม่เข้าไปอยู่ เกิดกับการแบ่งแบบขนาดแปรผัน (Dynamic Partitioning, Segmentation)
2.2 ระบบหนึ่งแบ่งหน่วยความจำเป็นพาร์ติชันคงที่ขนาด 64 KB จำนวน 4 พาร์ติชัน และมีโพรเซสขนาด 40 KB, 58 KB, 12 KB และ 63 KB ถูกบรรจุลงพาร์ติชันละ 1 โพรเซส จงคำนวณการสูญเสียพื้นที่ย่อยภายในของแต่ละพาร์ติชันและผลรวมทั้งระบบ พร้อมระบุเปอร์เซ็นต์ของหน่วยความจำที่สูญเปล่า
ตอบ: คำนวณพื้นที่ย่อยภายในที่สูญเปล่า (Internal Fragmentation):
• พาร์ติชัน 1 (ใส่โพรเซส 40 KB): เสียภายใน = 64 - 40 = 24 KB
• พาร์ติชัน 2 (ใส่โพรเซส 58 KB): เสียภายใน = 64 - 58 = 6 KB
• พาร์ติชัน 3 (ใส่โพรเซส 12 KB): เสียภายใน = 64 - 12 = 52 KB
• พาร์ติชัน 4 (ใส่โพรเซส 63 KB): เสียภายใน = 64 - 63 = 1 KB
ผลรวมการสูญเสียพื้นที่ภายในทั้งระบบ = 24 + 6 + 52 + 1 = 83 KB
เปอร์เซ็นต์หน่วยความจำที่สูญเปล่า = (83 / 256) * 100 = 32.42% (เกือบ 1 ใน 3 สูญเปล่าฟรีๆ!)
2.3 จงอธิบายวิธีการอัดแน่น (Compaction) ว่าช่วยแก้ปัญหาใด ต้องแลกมาด้วยต้นทุนอะไร และเหตุใดระบบที่ใช้การเชื่อมโยงตำแหน่งแบบ compile time จึงไม่สามารถทำการอัดแน่นได้
ตอบ: • ช่วยแก้ปัญหา: External Fragmentation โดยการกวาดโพรเซสที่กระจัดกระจายไปกองรวมกันฝั่งหนึ่ง เพื่อรวมเศษพื้นที่ว่างให้กลายเป็นผืนใหญ่ก้อนเดียว
• ต้นทุนที่ต้องแลก: เสียเวลา CPU และ I/O มหาศาลในการก๊อปปี้ข้อมูลย้ายเมมโมรี เครื่องจะกระตุกชั่วคราว
• ทำไม Compile Time ทำไม่ได้: เพราะระบบแบบ Compile Time ล็อกตำแหน่ง Address แบบตายตัวไปในโค้ดแล้ว ถ้ากวาดเลื่อนที่ในแรม ตัวชี้และคำสั่งจะชี้มั่วทันที ระบบที่จะทำ Compaction ได้ต้องผูกตำแหน่งแบบ Run-Time เท่านั้น
2.4 เหตุใดเทคนิคเพจจิ้งจึงขจัดปัญหา External Fragmentation ได้ แต่กลับทำให้เกิด Internal Fragmentation แทน จงอธิบายพร้อมยกตัวอย่างเชิงตัวเลขประกอบ
ตอบ: • ขจัด External Fragmentation: เพราะ Paging หั่นแรมเป็นบล็อกเท่ากันเป๊ะเรียกว่า 'เฟรม' (Frame) โพรเซสจะไปอยู่ที่ไหนก็ได้ ไม่ต้องอยู่ติดกันเป็นผืนเดียว (Non-contiguous) มีเฟรมว่างตรงไหนก็จับยัดได้หมด จึงไม่มีเศษพื้นที่ที่ต่อกันไม่ติด
• เกิด Internal Fragmentation แทน: เพราะขนาดของโปรแกรมมันไม่ได้หารลงตัวด้วยขนาดเพจเสมอไป เพจสุดท้ายของโปรแกรมเลยใช้ไม่เต็ม
• ตัวอย่างตัวเลข: ขนาดเพจ 4 KB แต่โปรแกรมขอ 13 KB ระบบต้องให้ 4 เพจ (16 KB) เพจที่สี่ใช้ไปแค่ 1 KB เหลือเศษทิ้งข้างใน 3 KB
ข้อ 3. แนวคิดหน่วยความจำเสมือน (10 คะแนน)
3.1 จงอธิบายหลักการของการจัดสรรหน้าตามคำร้องขอ (Demand Paging) และระบุบทบาทของบิตสถานะ (valid-invalid bit) ในตารางเพจ
ตอบ: • Demand Paging: หลักการคือ 'ไม่เรียกใช้ ไม่โหลดเข้าแรม' (Lazy Paging) โหลดเพจเข้ามาเฉพาะตอนที่คำสั่งจะแตะต้องมันจริงๆ
• บทบาทของ Valid-Invalid Bit:
  - Valid (v): เพจนี้อยู่ในแรมแล้ว อ่านเขียนได้ทันที
  - Invalid (i): เพจนี้ยังนอนอยู่ในดิสก์ หรือไม่มีสิทธิ์แตะ ถ้าซีพียูเรียกใช้เพจที่เป็น i ฮาร์ดแวร์จะส่งสัญญาณฟ้องเกิด Page Fault ทันที
3.2 จงเรียงลำดับขั้นตอนการจัดการเมื่อเกิดการผิดหน้า (Page Fault) ให้ครบทุกขั้นตอนตั้งแต่โพรเซสอ้างอิงตำแหน่งจนกระทั่งโพรเซสทำงานต่อได้ และระบุว่าขั้นตอนใดใช้เวลานานที่สุด เพราะเหตุใด
ตอบ: ลำดับ 8 ขั้นตอนเมื่อเกิด Page Fault:
1. ซีพียูเช็คตารางเพจ เจอสถานะเป็น i (Invalid)
2. ฮาร์ดแวร์ส่งสัญญาณ Trap ไปฟ้องระบบปฏิบัติการ
3. OS เข้าควบคุม เซฟสถานะโพรเซสเดิม แล้วเช็คว่าขอถูกกฎหมายไหม (ถ้ามั่วสั่ง Abort ทันที)
4. OS ควานหาเฟรมว่างในแรม (ถ้าไม่มีเฟรมว่าง ต้องรันอัลกอริทึมเตะเพจอื่นออก)
5. สั่งอ่านเพจที่ต้องการจากดิสก์มาเขียนลงเฟรมว่าง
6. ดิสก์อ่านเสร็จ ส่งสัญญาณ Interrupt กลับมาบอก OS
7. OS อัปเดตตารางเพจ ใส่หมายเลขเฟรมและเปลี่ยนบิตเป็น v
8. รีสตาร์ตคำสั่งเดิมที่ค้างอยู่ ให้กลับมาทำงานต่อได้ราบรื่น

ขั้นตอนที่ช้าสุด: 'ขั้นตอนที่ 5 (อ่านดิสก์เข้าแรม)' ช้ากว่าขั้นตอนอื่นเป็นแสนเท่า เพราะแรมวิ่งระดับนาโนวินาที แต่ดิสก์วิ่งระดับมิลลิวินาที
3.3 จงอธิบายว่าเหตุใดหน่วยความจำเสมือนจึงทำให้โปรแกรมขนาด 100 MB ทำงานบนเครื่องที่มีหน่วยความจำหลัก 64 MB ได้ และระบุข้อจำกัดที่ยังคงมีอยู่
ตอบ: • ทำไมรันได้: โปรแกรมไม่ได้ใช้โค้ดทั้ง 100 MB พร้อมกันในเสี้ยววินาทีเดียวหรอกเนาะ (ตามหลัก Locality) Virtual Memory จะโหลดเฉพาะส่วนที่กำลังรันอยู่ (Working Set) เช่น 15-20 MB เข้ามาในแรม ส่วนที่เหลือทิ้งไว้ในดิสก์
• ข้อจำกัด: พื้นที่ Swap บนดิสก์ต้องมีพอ และถ้าเปิดหลายโปรแกรมพร้อมกันจน Working Set รวมล้นแรม เครื่องจะเกิด Thrashing สลับข้อมูลเข้าออกดิสก์จนค้าง
3.4 จงอธิบายกลไก Copy-on-Write ที่ใช้เมื่อเรียกฟังก์ชัน fork() ว่าช่วยให้การสร้างโพรเซสใหม่รวดเร็วขึ้นอย่างไร และเกิดอะไรขึ้นเมื่อโพรเซสลูกเขียนข้อมูลลงเพจที่แชร์กันอยู่
ตอบ: • ช่วยให้เร็วขึ้นยังไง: ตอนสั่ง fork() ระบบจะไม่ก๊อปปี้แรมของโพรเซสพ่อให้ลูก แต่ให้ลูก 'แชร์หน้าเพจร่วมกับพ่อไปเลย' แล้วล็อกสิทธิ์เป็น Read-Only สร้างลูกได้ในพริบตาเดียว
• เกิดอะไรขึ้นเมื่อลูกเขียนข้อมูล: พอโพรเซสลูกจะเขียนข้อมูลลงเพจ OS จะดักจับแล้วแอบก๊อปปี้เพจนั้นแยกออกมาเป็นใบใหม่เฉพาะจุดที่มีการเขียน ให้ลูกได้เพจใหม่ไปคนเดียว ส่วนเพจอื่นที่แค่อ่านก็แชร์กันต่อไป ประหยัดแรมและเวลาจัดๆ
ตอนที่ 2 การแบ่งพื้นที่เป็นหน้า การแบ่งส่วน และการจัดวาง (2 ข้อ ข้อละ 15 คะแนน รวม 30 คะแนน)
ข้อ 1. การแปลที่อยู่ ตารางเพจ และ TLB (15 คะแนน)
ส่วนที่ 1: ให้พิจารณาระบบคอมพิวเตอร์ขนาด 32 บิต ที่มีขนาดเพจเท่ากับ 4 KB และมีหน่วยความจำกายภาพ 1 GB
1.1 จงคำนวณค่าต่อไปนี้พร้อมแสดงวิธีคิด: (ก) จำนวนบิตของ page offset และ page number (ข) จำนวนหน้าสูงสุดในพื้นที่ที่อยู่ทางตรรกะ (ค) จำนวนเฟรมในหน่วยความจำกายภาพ และจำนวนบิตของหมายเลขเฟรม (ง) ขนาดของตารางเพจ 1 ตาราง เมื่อ 1 เอนทรีมีขนาด 4 ไบต์
ตอบ: (ก) เพจ 4 KB = 2 ยกกำลัง 12 ไบต์ -> Page Offset = 12 บิต / ที่อยู่ 32 บิต -> Page Number = 32 - 12 = 20 บิต
(ข) จำนวนหน้าสูงสุดใน Logical Space = 2 ยกกำลัง 20 = 1,048,576 หน้า (1M หน้า)
(ค) แรม 1 GB = 2 ยกกำลัง 30 ไบต์, เฟรม 4 KB = 2 ยกกำลัง 12 ไบต์ -> จำนวนเฟรม = 2 ยกกำลัง 18 = 262,144 เฟรม (256K เฟรม) / จำนวนบิตหมายเลขเฟรม = 18 บิต
(ง) ขนาดตารางเพจ 1 ตาราง = 1,048,576 เอนทรี * 4 ไบต์ = 4,194,304 ไบต์ = 4 MB
1.2 หากระบบเปลี่ยนไปใช้ตารางเพจแบบ 2 ระดับ โดยแบ่งหมายเลขหน้าเป็น p1 = 10 บิต และ p2 = 10 บิต จงคำนวณขนาดของตารางระดับนอกและตารางระดับในแต่ละตาราง แล้วอธิบายว่าโครงสร้างนี้ช่วยประหยัดหน่วยความจำได้อย่างไรเมื่อโพรเซสใช้พื้นที่ที่อยู่เพียงบางส่วน
ตอบ: • ขนาดตารางระดับนอก (Outer Page Table) = 2 ยกกำลัง 10 * 4 ไบต์ = 1,024 * 4 ไบต์ = 4 KB (พอดี 1 เพจ)
• ขนาดตารางระดับในแต่ละตาราง (Inner Page Table) = 2 ยกกำลัง 10 * 4 ไบต์ = 4 KB ต่อตาราง
• ช่วยประหยัดหน่วยความจำยังไง: ตารางชั้นเดียวต้องจองแรม 4 MB รวดเดียวแม้โปรแกรมจะใช้แค่ 8 KB แต่ตาราง 2 ระดับ เราสร้าง Outer Table แค่ 4 KB ส่วน Inner Table จะสร้างเฉพาะช่วงที่โปรแกรมมีการใช้งานจริงเท่านั้น ช่วงไหนว่างก็ปล่อยเป็น Null ไว้ ไม่ต้องสร้าง ประหยัดแรมมหาศาล
ส่วนที่ 2: ให้พิจารณาระบบขนาดเล็กอีกระบบหนึ่ง ซึ่งมีขนาดเพจเท่ากับ 1 KB (1,024 ไบต์) และมีตารางเพจของโพรเซส A ดังนี้
1.3 จงแปลงตำแหน่งทางตรรกะต่อไปนี้ให้เป็นตำแหน่งทางกายภาพ โดยแสดงการคำนวณหมายเลขหน้าและขอบเขตหน้า (offset) ทุกข้อ: (ก) 620 (ข) 1,234 (ค) 3,500 (ง) 5,632 (จ) 4,096
ตอบ: สูตรคำนวณ: p = LA // 1024, d = LA % 1024, PA = (f * 1024) + d
(ก) 620: p = 0, d = 620 -> หน้า 0 อยู่เฟรม 12 (v) -> PA = (12 * 1024) + 620 = 12,908
(ข) 1,234: p = 1, d = 210 -> หน้า 1 อยู่เฟรม 9 (v) -> PA = (9 * 1024) + 210 = 9,426
(ค) 3,500: p = 3, d = 428 -> หน้า 3 อยู่เฟรม 2 (v) -> PA = (2 * 1024) + 428 = 2,476
(ง) 5,632: p = 5, d = 512 -> หน้า 5 อยู่เฟรม 7 (v) -> PA = (7 * 1024) + 512 = 7,680
(จ) 4,096: p = 4, d = 0 -> หน้า 4 มีสถานะเป็น 'i' (Invalid) -> เกิด Page Fault! (แปลงไม่ได้ ต้องโหลดเพจเข้าแรมก่อน)
1.4 ตำแหน่งทางกายภาพ 10,000 ตรงกับตำแหน่งทางตรรกะใดของโพรเซส A จงแสดงวิธีคิดย้อนกลับ
ตอบ: วิธีคิดย้อนกลับ:
1. หาเฟรมและออฟเซ็ต: เฟรม f = 10,000 // 1024 = 9, ออฟเซ็ต d = 10,000 % 1024 = 784
2. ส่องดูตารางเพจ: เฟรม 9 ถูกถือครองโดย 'หน้า 1 (p = 1)'
3. คำนวณตำแหน่งตรรกะ = (p * 1024) + d = (1 * 1024) + 784 = 1,808
1.5 ระบบนี้ติดตั้ง TLB โดยการค้นหาใน TLB ใช้เวลา 15 ns และการเข้าถึงหน่วยความจำหลักใช้เวลา 90 ns หากอัตราการพบใน TLB (hit ratio) เท่ากับ 85%
ก) จงคำนวณเวลาเฉลี่ยในการเข้าถึงหน่วยความจำ (EMAT) พร้อมแสดงวิธีคิด
ข) เวลาที่ได้ช้ากว่าการเข้าถึงหน่วยความจำโดยตรงกี่เปอร์เซ็นต์
ค) หากต้องการให้ EMAT ไม่เกิน 110 ns อัตราการพบใน TLB ต้องเป็นอย่างน้อยเท่าใด
ตอบ: ก) EMAT = (0.85 * (15 + 90)) + (0.15 * (15 + 90 + 90)) = (0.85 * 105) + (0.15 * 195) = 89.25 + 29.25 = 118.50 ns
ข) ช้ากว่าเข้าแรมตรงกี่เปอร์เซ็นต์: เข้าแรมตรงใช้ 90 ns -> ((118.50 - 90) / 90) * 100 = 31.67%
ค) อยากให้ EMAT <= 110 ns:
   h * 105 + (1 - h) * 195 <= 110 -> 195 - 90h <= 110 -> 90h >= 85 -> h >= 85 / 90 = 94.44%
1.6 มีผู้ใช้ 60 คนเรียกใช้โปรแกรมแก้ไขข้อความเดียวกัน ซึ่งมีส่วนรหัสคำสั่งแบบ reentrant ขนาด 120 KB และแต่ละผู้ใช้มีพื้นที่ข้อมูลส่วนตัว 40 KB จงคำนวณหน่วยความจำที่ต้องใช้ในกรณีที่ไม่มีการใช้เพจร่วมกัน เทียบกับกรณีที่ใช้เพจร่วมกัน และคำนวณเปอร์เซ็นต์ที่ประหยัดได้
ตอบ: • กรณีไม่แชร์เพจ: คนละ (120 + 40) = 160 KB -> 60 คนใช้ = 60 * 160 = 9,600 KB (9.6 MB)
• กรณีแชร์เพจ (Shared Pages): โค้ดชุดเดียว 120 KB + ข้อมูล 60 คน (60 * 40 = 2,400) = 2,520 KB (2.52 MB)
• เปอร์เซ็นต์ที่ประหยัดได้ = ((9,600 - 2,520) / 9,600) * 100 = 73.75% (ประหยัดแรมไปเกือบ 3 ใน 4)
ข้อ 2. การจัดวางในหน่วยความจำและการแบ่งส่วน (15 คะแนน)
ระบบหนึ่งใช้การจัดสรรหน่วยความจำแบบพาร์ติชันไดนามิก ขณะหนึ่งมีช่องว่าง (hole) เรียงตามตำแหน่งในหน่วยความจำจากต่ำไปสูงดังนี้ 150 KB, 520 KB, 180 KB, 320 KB และ 640 KB จากนั้นมีโพรเซสร้องขอพื้นที่เข้ามาตามลำดับคือ 210 KB, 430 KB, 120 KB และ 450 KB
2.1 จงจัดวางโพรเซสทั้งสี่ด้วยวิธี First-fit, Best-fit และ Worst-fit โดยทำตารางแสดงว่าโพรเซสใดถูกวางในช่องว่างใด และเหลือช่องว่างขนาดเท่าใดหลังการวางแต่ละครั้ง
ตอบ: สรุปผล: Best-fit จัดวางได้ครบทั้ง 4 ตัวอย่างสมบูรณ์ ส่วน First-fit และ Worst-fit วาง P4 ไม่ได้
2.2 จากผลในข้อ 2.1 วิธีใดบ้างที่ไม่สามารถจัดวางโพรเซสได้ครบทั้งสี่ตัว และโพรเซสใดที่ต้องรอ จงระบุพร้อมคำนวณพื้นที่ว่างรวมที่ยังเหลืออยู่ในขณะนั้น แล้วอธิบายว่าเหตุใดพื้นที่ว่างรวมจึงมากพอแต่กลับใช้งานไม่ได้
ตอบ: • วิธีที่วางไม่ครบ: First-fit และ Worst-fit (โพรเซสที่ต้องรอคือ P4 ขนาด 450 KB)
• พื้นที่ว่างรวมที่ยังเหลืออยู่ขณะนั้น: 30 + 310 + 180 + 320 + 210 = 1,050 KB
• ทำไมมีที่ตั้ง 1,050 KB แต่ใช้ไม่ได้: เพราะเกิด External Fragmentation พื้นที่ว่างมันแตกเป็นเศษเล็กเศษน้อยกระจัดกระจาย ไม่ได้อยู่ติดกันเป็นผืนเดียว เลยยัด P4 ที่ต้องการ 450 KB ก้อนเดียวไม่ลง
2.3 หากระบบทำการอัดแน่น (Compaction) ในกรณีของ First-fit จงระบุว่าจะได้ช่องว่างผืนเดียวขนาดเท่าใด และโพรเซสที่รออยู่จะถูกบรรจุได้หรือไม่
ตอบ: • ขนาดช่องว่างผืนเดียวหลังอัดแน่น = รวมเศษทั้งหมด = 1,050 KB
• P4 ที่รออยู่จะถูกบรรจุได้หรือไม่: บรรจุได้แน่นอน 100%! เพราะ P4 ขอแค่ 450 KB พอรวมเป็นก้อน 1,050 KB ก็ใส่ได้สบาย และยังเหลือที่ว่างอีก 600 KB
ให้พิจารณาระบบที่ใช้การแบ่งส่วน (Segmentation) โดยมีตารางเซ็กเมนต์ของโพรเซส B ดังนี้
2.4 จงแปลงการอ้างอิงแบบ (s, d) ต่อไปนี้ให้เป็นตำแหน่งทางกายภาพ หรือระบุว่าเกิดข้อผิดพลาดการอ้างอิงเกินขอบเขต พร้อมแสดงการตรวจสอบเงื่อนไขทุกข้อ: (ก) (0, 430) (ข) (1, 280) (ค) (2, 1,100) (ง) (3, 600) (จ) (2, 0)
ตอบ: ตรวจสอบเงื่อนไข: d < limit หรือไม่ ถ้าผ่าน PA = base + d
(ก) (0, 430): 430 < 900 (ผ่าน) -> PA = 2,100 + 430 = 2,530
(ข) (1, 280): 280 < 250 (เท็จ เกิน limit) -> เกิดข้อผิดพลาด Addressing Error / Trap
(ค) (2, 1,100): 1,100 < 1,200 (ผ่าน) -> PA = 3,700 + 1,100 = 4,800
(ง) (3, 600): 600 < 600 (เท็จ ออฟเซ็ตนับ 0 ถึง limit-1 คือ 0-599 เท่านั้น) -> เกิดข้อผิดพลาด Addressing Error / Trap
(จ) (2, 0): 0 < 1,200 (ผ่าน) -> PA = 3,700 + 0 = 3,700
2.5 จงเปรียบเทียบการแบ่งหน้า (Paging) กับการแบ่งส่วน (Segmentation) ในประเด็นต่อไปนี้ ขนาดของหน่วยที่แบ่ง มุมมองของโปรแกรมเมอร์ ชนิดของการสูญเสียพื้นที่ย่อยที่เกิดขึ้น และความสะดวกในการกำหนดสิทธิ์การเข้าถึงและการใช้ร่วมกัน แล้วสรุปว่าเหตุใดสถาปัตยกรรมสมัยใหม่จึงเลือกใช้ Paging เป็นหลัก
ตอบ: เปรียบเทียบหมัดต่อหมัด:
• ขนาดหน่วย: Paging มีขนาดคงที่แน่นอน (เช่น 4 KB) กำหนดโดยฮาร์ดแวร์ / Segmentation มีขนาดแปรผันตามขนาดของโมดูลโค้ดจริง
• มุมมองโปรแกรมเมอร์: Paging มองไม่เห็น (Transparent) เห็นแรมแบนราบผืนเดียว / Segmentation ตรงกับมุมมองโปรแกรมเมอร์โดยตรง (แยกฟังก์ชัน, โค้ด, สแตก)
• การสูญเสียพื้นที่: Paging เกิดเฉพาะ Internal Fragmentation / Segmentation เกิดเฉพาะ External Fragmentation
• การกำหนดสิทธิ์และแชร์: Segmentation สะดวกและเป็นธรรมชาติกว่ามาก เพราะแบ่งตามขอบเขตของโค้ด/ข้อมูลจริง / Paging ทำได้ยากกว่าเพราะบล็อก 4 KB อาจตัดผ่ากลางฟังก์ชัน
• ทำไมยุคใหม่ใช้ Paging: เพราะจัดการแรมง่ายกว่ามหาศาล ไม่มีปัญหา External Fragmentation ไม่ต้องมาคอยกวาดอัดแน่น (Compaction) ย้ายข้อมูลให้เครื่องกระตุก
ตอนที่ 3 หน่วยความจำเสมือนและการสับเปลี่ยนหน้า (2 ข้อ ข้อละ 15 คะแนน รวม 30 คะแนน)
ข้อ 1. อัลกอริทึมการสับเปลี่ยนหน้า (15 คะแนน)
กำหนดลำดับการอ้างอิงหน้า (Reference String) ดังนี้: 2, 3, 2, 1, 5, 2, 4, 5, 3, 2, 5, 2 โดยเริ่มต้นหน่วยความจำว่างทั้งหมด ในข้อ 1.1 ถึง 1.3 ให้ใช้จำนวนเฟรมเท่ากับ 3 เฟรม และให้เขียนตารางแสดงสถานะของทุกเฟรมในทุกครั้งที่มีการอ้างอิง พร้อมทำเครื่องหมายระบุครั้งที่เกิดการผิดหน้า
1.1 อัลกอริทึมแบบมาก่อน-ออกก่อน (FIFO) พร้อมนับจำนวนครั้งของการผิดหน้า
ตอบ: จำลองสถานะ 3 เฟรมของ FIFO (F = Page Fault, H = Hit):
• t=1 (ref 2): [2, -, -] (F1)
• t=2 (ref 3): [2, 3, -] (F2)
• t=3 (ref 2): [2, 3, -] (H)
• t=4 (ref 1): [2, 3, 1] (F3)
• t=5 (ref 5): 2 มาก่อนสุด เตะ 2 -> [5, 3, 1] (F4)

1.4 จงสรุปผลลงในตารางเปรียบเทียบด้านล่าง คำนวณอัตราการผิดหน้า (Page Fault Rate) ของแต่ละวิธี แล้วอธิบายว่าเหตุใดวิธี Optimal จึงให้ผลดีที่สุดแต่กลับนำไปใช้จริงไม่ได้
ตอบ: ทำไม Optimal ดีสุดแต่ใช้จริงไม่ได้: เพราะมันต้องหยั่งรู้อนาคตล่วงหน้า ซึ่งในชีวิตจริง OS ไม่มีญาณทิพย์หรอกเนาะ มีไว้ใช้เป็นไม้บรรทัดเทียบในทฤษฎีเท่านั้น
รูปที่ 1 เปรียบเทียบอัลกอริทึมการสับเปลี่ยนหน้า และปรากฏการณ์ Belady's Anomaly
1.5 ให้พิจารณาลำดับการอ้างอิงชุดใหม่ คือ 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 จงคำนวณจำนวนครั้งของการผิดหน้าด้วยวิธี FIFO ทั้งกรณีที่มี 3 เฟรม และ 4 เฟรม แล้วอธิบายผลที่ได้ว่าเรียกว่าปรากฏการณ์ใด เหตุใดจึงขัดกับสามัญสำนึก และวิธี LRU เกิดปรากฏการณ์นี้ได้หรือไม่
ตอบ: คำนวณ FIFO:
• กรณี 3 เฟรม: เกิด Page Fault รวม 9 ครั้ง
• กรณี 4 เฟรม: เกิด Page Fault รวม 10 ครั้ง!
• ชื่อปรากฏการณ์: 'Belady’s Anomaly (ความผิดปกติของเบลาดี้)'
• ขัดสามัญสำนึกยังไง: ให้แรมเพิ่มขึ้นแท้ๆ แต่ Page Fault ดันเพิ่มขึ้นแทนที่จะลดลง
• LRU เกิดได้ไหม: ไม่มีทางเกิดเด็ดขาด เพราะ LRU เป็น Stack Algorithm ที่การันตีว่าของใน n เฟรมจะเป็น subset ของ n+1 เฟรมเสมอ
1.6 ระบบหนึ่งใช้วิธี NRU (Not Recently Used) โดยขณะเกิดการผิดหน้ามีเพจในหน่วยความจำพร้อมค่าบิต R (referenced) และ M (modified) ดังตาราง จงจัดเพจทั้งหมดเข้ากลุ่มที่ 0 ถึง 3 ตามหลักการของ NRU แล้วระบุว่าเพจใดควรถูกสับเปลี่ยนออกเป็นลำดับแรก พร้อมอธิบายเหตุผล และเปรียบเทียบว่าวิธีให้โอกาสครั้งที่สอง (Second Chance) ต่างจาก NRU อย่างไร
ตอบ: • จัดเข้ากลุ่ม 0 ถึง 3 ตามหลัก NRU:
  - กลุ่ม 0 (R=0, M=0): เพจ D (ไม่ได้เรียกใช้ ไม่ได้แก้ไข)
  - กลุ่ม 1 (R=0, M=1): เพจ B (ไม่ได้เรียกใช้ แต่มีการแก้ไข)
  - กลุ่ม 2 (R=1, M=0): เพจ C, E (เพิ่งเรียกใช้ แต่ไม่ได้แก้ไข)
  - กลุ่ม 3 (R=1, M=1): เพจ A (เพิ่งเรียกใช้ และมีการแก้ไข)

• เพจที่ถูกเตะออกลำดับแรก: 'เพจ D' เพราะอยู่กลุ่ม 0 ต่ำสุด ไม่ได้แตะนานแล้วแถมไม่ต้องเสียเวลาเขียนเซฟลงดิสก์

• Second Chance ต่างจาก NRU อย่างไร: Second Chance ยืนพื้นด้วยคิว FIFO แบบเข็มนาฬิกา ถ้าเจอ R=1 จะให้โอกาสรอดโดยปรับ R=0 แล้ววนต่อจนเจอ R=0 ถึงจะเตะ ส่วน NRU กวาดจัดเข้า 4 กลุ่มใหญ่แล้วสุ่มหยิบตัวในกลุ่มต่ำสุดทันทีโดยไม่สนคิว FIFO
ข้อ 2. ประสิทธิภาพ การจัดสรรเฟรม และภาวะ Thrashing (15 คะแนน)
2.1 ระบบหนึ่งมีเวลาเข้าถึงหน่วยความจำเฉลี่ย 100 ns และใช้เวลาจัดการการผิดหน้า 1 ครั้งเท่ากับ 6 ms
ก) หากความน่าจะเป็นที่จะเกิดการผิดหน้า p = 0.001 จงคำนวณเวลาเข้าถึงหน่วยความจำจริง (Effective Access Time) พร้อมแสดงสมการ
ข) ระบบทำงานช้าลงกี่เท่าเมื่อเทียบกับการเข้าถึงหน่วยความจำปกติ
ค) หากต้องการให้ระบบช้าลงไม่เกิน 2 เท่า (EAT ไม่เกิน 200 ns) ค่า p สูงสุดที่ยอมรับได้เป็นเท่าใด และหมายความว่าเกิดการผิดหน้าได้ไม่เกิน 1 ครั้งต่อการอ้างอิงกี่ครั้ง
ตอบ: ก) EAT = (1 - p) * 100 + p * 6,000,000
   แทนค่า p = 0.001: EAT = (0.999 * 100) + (0.001 * 6,000,000) = 99.9 + 6,000 = 6,099.90 ns (~6.1 us)
ข) ช้าลงกี่เท่า: 6,099.90 / 100 = 61.00 เท่า! (พลาดแค่ 0.1% เครื่องช้าลง 61 เท่าตัว)
ค) ให้ช้าลงไม่เกิน 2 เท่า (EAT <= 200 ns):
   100 + 5,999,900 * p <= 200 -> p <= 100 / 5,999,900 = 0.00001667 (เกิด Page Fault ได้ไม่เกิน 1 ครั้งต่อการอ้างอิงประมาณ 60,000 ครั้ง!)
2.2 ระบบหนึ่งมีเฟรมว่างให้จัดสรร 180 เฟรม และมีโพรเซส 3 ตัวขนาด 60 KB, 120 KB และ 180 KB จงคำนวณจำนวนเฟรมที่แต่ละโพรเซสได้รับด้วยวิธี Equal Allocation และ Proportional Allocation แล้ววิเคราะห์ว่าวิธีใดเหมาะสมกว่าในกรณีนี้ เพราะเหตุใด
ตอบ: • Equal Allocation (แบ่งเท่ากัน): ได้คนละ 180 / 3 = 60 เฟรมเท่ากันหมด
• Proportional Allocation (แบ่งตามสัดส่วน ขนาดรวม 360 KB):
  - P1 (60 KB): (60 / 360) * 180 = 30 เฟรม
  - P2 (120 KB): (120 / 360) * 180 = 60 เฟรม
  - P3 (180 KB): (180 / 360) * 180 = 90 เฟรม
• วิธีที่เหมาะสม: 'Proportional Allocation เหมาะกว่าเห็นๆ' เพราะงานใหญ่ขนาด 180 KB ย่อมต้องการพื้นที่รันมากกว่า ถ้าให้เท่ากัน งานใหญ่จะขาดแคลนเฟรมจนเกิด Page Fault รัวๆ ขณะที่งานเล็กได้เฟรมเกินจนเหลือทิ้ง
2.3 จงเปรียบเทียบ Global Replacement กับ Local Replacement พร้อมอธิบายว่าเหตุใด Global Replacement จึงทำให้ภาวะ Thrashing ลุกลามจากโพรเซสหนึ่งไปยังโพรเซสอื่นได้
ตอบ: • เปรียบเทียบ: Global แย่งเฟรมของใครก็ได้ในระบบ / Local เตะได้เฉพาะเฟรมในโควตาตัวเอง
• ทำไม Global ทำให้ Thrashing ลุกลาม: พองานหนึ่งเฟรมไม่พอ มันจะไปขโมยเฟรมของเพื่อน เพื่อนก็เฟรมไม่พอตาม เลยไปขโมยต่อเป็นทอดๆ จนทุกตัวกอดคอกันขาดแรม กลายเป็นแย่งกันอ่านดิสก์ทั้งระบบ พังหมด
2.4 จงอธิบายภาวะ Thrashing โดยอ้างอิงกราฟความสัมพันธ์ระหว่างระดับของ Multiprogramming กับการใช้งานหน่วยประมวลผลกลาง และตอบว่าเหตุใดเมื่อเพิ่มจำนวนโพรเซสเกินจุดหนึ่งแล้วการใช้งานหน่วยประมวลผลกลางจึงลดลงอย่างรวดเร็ว
ตอบ: • อธิบายกราฟ: ช่วงแรกยิ่งเพิ่มจำนวนโพรเซส CPU ยิ่งทำงานคุ้มค่าพุ่งสูงขึ้น แต่พอเพิ่มจนเกินจุดวิกฤต (Peak) CPU จะดิ่งลงเหวแตะศูนย์ทันที
• ทำไมลดลงฮวบ: เพราะแรมไม่พอแจก ทุกโพรเซสเกิด Page Fault พร้อมกัน พองานติดรออ่านดิสก์ ซีพียูก็ว่าง OS ดันเข้าใจผิดคิดว่างานน้อย เลยเปิดงานใหม่เข้ามาซ้ำเติม แรมยิ่งขาดหนัก ทุกตัวเลยไปออคิวรออ่านดิสก์ ซีพียูนั่งตบยุงเฉยๆ
รูปที่ 2 กราฟความสัมพันธ์ระหว่างระดับของ Multiprogramming กับการใช้งาน CPU (ภาวะ Thrashing)
2.5 จงเสนอวิธีแก้ปัญหา Thrashing มา 2 วิธี พร้อมอธิบายหลักการทำงานของแต่ละวิธี และอธิบายว่าแบบจำลอง Locality ช่วยให้ระบบกำหนดจำนวนเฟรมที่เหมาะสมให้แต่ละโพรเซสได้อย่างไร
ตอบ: • 2 วิธีแก้ Thrashing:
  1. Working-Set Model: คอยเช็คขนาดแรมที่แต่ละตัวต้องใช้จริง (WSS) ถ้ารวมกันแล้วเกินแรมเครื่อง สั่ง Pause / Swap-out บางโพรเซสออกไปก่อน
  2. Page-Fault Frequency (PFF): วัดความถี่ Page Fault ถ้าตัวไหนพุ่งเกินเกณฑ์ ให้เติมเฟรมเพิ่ม ถ้าเฟรมหมดเครื่อง ให้ดึงงานบางตัวออกไปพัก
• แบบจำลอง Locality ช่วยยังไง: โปรแกรมจะเรียกใช้ข้อมูลเป็นกระจุกๆ (Locality) ในช่วงเวลานั้น ถ้าระบบจัดเฟรมให้พอดีคลุม Locality นั้นได้ โพรเซสจะรันลื่นไหลแทบไม่เกิด Page Fault เลย
ตอนที่ 4 โจทย์ประยุกต์กับสถานการณ์จริง (1 ข้อ 10 คะแนน)
ข้อ 1. เซิร์ฟเวอร์ประมวลผลภาพถ่ายดาวเทียม (10 คะแนน)
หน่วยงานแห่งหนึ่งใช้เซิร์ฟเวอร์ที่มีหน่วยความจำหลัก 8 GB ขนาดเพจ 4 KB เพื่อประมวลผลภาพถ่ายดาวเทียม โดยรันงานประมวลผลภาพพร้อมกัน 12 งาน แต่ละงานต้องอ่านข้อมูลภาพขนาด 2 GB แบบสุ่มตำแหน่ง ผู้ดูแลระบบตรวจสอบพบว่าการใช้งานหน่วยประมวลผลกลางอยู่ที่ประมาณ 10% ขณะที่ดิสก์ทำงานอยู่ที่ 95% ตลอดเวลา และงานทั้งหมดคืบหน้าช้ามาก
1.1 จงวินิจฉัยว่าระบบกำลังเผชิญปัญหาใด โดยอ้างอิงตัวเลขที่ตรวจวัดได้ และอธิบายกลไกที่ทำให้เกิดอาการดังกล่าวทีละขั้นตอน
ตอบ: • ฟันธง: ระบบกำลังเกิด 'ภาวะ Thrashing ขั้นรุนแรง'
• อ้างอิงตัวเลขและกลไก: 12 งาน งานละ 2 GB ต้องการแรมรวมถึง 12 * 2 = 24 GB แต่เครื่องมีแรมจริงแค่ 8 GB (ขาดถึง 3 เท่า!) ยิ่งอ่านแบบสุ่ม (Random Access) ทำให้ Locality พังยับ เกิด Page Fault รัวๆ ดิสก์วิ่งชนเพดาน 95% ตลอดเวลาเพื่อสลับเพจ โพรเซสทั้งหมดเลยติดบล็อกรอ I/O ซีพียูเลยว่างจัดวิ่งแค่ 10% งานเลยไม่เดิน
1.2 จงเสนอแนวทางแก้ไขมา 3 แนวทาง พร้อมระบุข้อดีและข้อจำกัดของแต่ละแนวทาง โดยอย่างน้อย 1 แนวทางต้องเป็นวิธีที่ไม่ต้องเพิ่มฮาร์ดแวร์
ตอบ: 1. แนวทางที่ 1 (ไม่ต้องเพิ่มฮาร์ดแวร์ - แนะนำที่สุด): ลดระดับ Multiprogramming สั่งรันพร้อมกันแค่ทีละ 3-4 งาน (ใช้แรมรวม 6-8 GB พอดีกับแรมเครื่อง) ที่เหลือเข้าคิวรอ
   - ข้อดี: งานที่รันอยู่จะไม่เกิด Page Fault เลย ทำงานเต็มสปีด งานเสร็จไวกว่าปล่อยให้ค้าง 12 ตัวพร้อมกันมหาศาล และไม่ต้องเสียเงินสักบาท
   - ข้อจำกัด: งานบางตัวต้องยืนรอคิว ไม่ได้เริ่มรันทันที

2. แนวทางที่ 2 (ปรับปรุงโค้ดโปรแกรม): เปลี่ยนวิธีอ่านภาพเป็น Tiled / Blocked Processing แบ่งภาพเป็นบล็อกย่อยๆ แล้วประมวลผลทีละบล็อกให้จบ
   - ข้อดี: สร้าง Locality เทียมขึ้นมา ลดการสลับเพจเข้าออกดิสก์ลงอย่างมาก
   - ข้อจำกัด: ต้องแก้โค้ดโปรแกรมใหม่ทั้งหมด เสียเวลาพัฒนา

3. แนวทางที่ 3 (อัปเกรดฮาร์ดแวร์): เพิ่มแรมเป็น 32 GB ขึ้นไป หรือเปลี่ยนดิสก์เป็น NVMe SSD ความเร็วสูง
   - ข้อดี: รัน 12 งานพร้อมกันได้จริงตามที่ต้องการ ประสิทธิภาพพุ่งสูงสุด
   - ข้อจำกัด: ต้องเสียเงินซื้ออุปกรณ์ และมีข้อจำกัดเรื่องสล็อตของเมนบอร์ด
1.3 หากผู้ดูแลระบบเปลี่ยนขนาดเพจจาก 4 KB เป็น 2 MB จงวิเคราะห์ผลกระทบต่อ (ก) ขนาดของตารางเพจ (ข) การสูญเสียพื้นที่ย่อยภายใน และ (ค) จำนวนครั้งของการผิดหน้าเมื่อการอ้างอิงข้อมูลมีลักษณะเป็นกลุ่ม (locality) สูง
ตอบ: (ก) ขนาดของตารางเพจ: เล็กลงอย่างมหาศาล (ลดลง 512 เท่า!) เพราะจำนวนเพจลดลงจากเดิมมาก และช่วยลด TLB Miss ด้วย
(ข) การสูญเสียพื้นที่ย่อยภายใน: เพิ่มขึ้นแน่นอน เพราะเพจก้อนใหญ่ขึ้น เพจสุดท้ายของแต่ละงานอาจเหลือเศษทิ้งได้ถึงหลักเมกะไบต์
(ค) จำนวนครั้ง Page Fault เมื่อ Locality สูง: ลดลงชัดเจน เพราะดึงข้อมูลมาทีก้อนใหญ่ 2 MB ถ้าอ่านติดๆ กัน ข้อมูลที่ต้องการจะติดเข้ามาด้วยในรอบเดียว
1.4 การใช้เทคนิค Memory-Mapped File สำหรับการอ่านไฟล์ภาพ จะช่วยระบบนี้อย่างไรเมื่อเทียบกับการเรียกใช้ฟังก์ชัน read() ตามปกติ และหากหลายงานอ่านไฟล์ภาพเดียวกัน ระบบจะได้ประโยชน์เพิ่มเติมอย่างไร
ตอบ: • ช่วยระบบอย่างไรเทียบกับ read(): read() ต้องเสียเวลาทำ System Call บ่อยๆ และต้องก๊อปปี้ข้อมูล 2 ทอด (ดิสก์ -> Kernel Buffer -> User Buffer) แต่ mmap เอาไฟล์ภาพไปผูกกับ Virtual Address ของโปรแกรมตรงๆ อ่านผ่านพอยน์เตอร์ได้เลย (Zero-copy) และดึงข้อมูลเข้าแรมแบบ On-demand เท่าที่ใช้จริง
• ประโยชน์เมื่อหลายงานอ่านไฟล์เดียวกัน: เกิด Page Sharing ทุกงานสามารถแชร์หน้าเพจกายภาพชุดเดียวกันในแรมได้ทันที! แรมที่ใช้จะไม่คูณตามจำนวนงาน จากที่ต้องใช้ 24 GB จะเหลือแค่ก้อนเดียว 2 GB ในแรม ช่วยดับปัญหา Thrashing ได้ทันที
