คำชี้แจง:
• การบ้านนี้ครอบคลุมเนื้อหาบทที่ 5-6 ทั้งหมด ให้ศึกษาเอกสารประกอบการสอนก่อนลงมือทำ
• ส่งโดยตั้งชื่อไฟล์เป็นรหัสนิสิต เช่น 67021398_บีม.docx (ส่งเป็นไฟล์ word)
• เขียนตอบด้วยภาษาของตนเอง อธิบายละเอียด แสดงวิธีทำทุกขั้นตอนอย่างครบถ้วน
ตอนที่ 1 คำถามทบทวนความรู้และการวิเคราะห์เงื่อนไข (3 ข้อ ข้อละ 10 คะแนน รวม 30 คะแนน)
ข้อ 1. เงื่อนไขสี่ประการของภาวะติดตาย (10 คะแนน)
ระบบปฏิบัติการสี่ระบบใช้กลไกจัดการทรัพยากรที่ต่างกัน ดังนี้
ก) ระบบใช้เทคนิค spooling กับเครื่องพิมพ์ โดยทุกโพรเซสเขียนงานพิมพ์ลงคิวบนดิสก์ แล้วมีเดมอนเพียงตัวเดียวเป็นผู้ส่งงานเข้าเครื่องพิมพ์จริง
ข) ระบบบังคับให้โพรเซสประกาศและร้องขอทรัพยากรทั้งหมดที่ต้องการในครั้งเดียวก่อนเริ่มทำงาน หากได้ไม่ครบจะยังไม่ได้เริ่มทำงานเลย
ค) เมื่อโพรเซสร้องขอทรัพยากรเพิ่มแล้วไม่ได้รับทันที ระบบจะบังคับให้โพรเซสนั้นคืนทรัพยากรทั้งหมดที่ถืออยู่ แล้วเริ่มกระบวนการร้องขอใหม่ทั้งชุด
ง) ระบบกำหนดหมายเลขกำกับทรัพยากรทุกชนิด และบังคับให้ทุกโพรเซสร้องขอทรัพยากรตามลำดับหมายเลขจากน้อยไปมากเท่านั้น
1.1 จงระบุว่ากลไก ก) ถึง ง) แต่ละข้อเป็นการทำลายเงื่อนไขของภาวะติดตายข้อใด (การไม่เกิดร่วม / ถือและรอ / ไม่มีการบังคับ / การรอแบบวงกลม) พร้อมอธิบายเหตุผลประกอบทุกข้อ
ตอบ: • กลไก ก) ทำลายเงื่อนไข: การไม่เกิดร่วม (Mutual Exclusion)
  เหตุผล: พรินเตอร์ปกติมันแชร์ใช้งานพร้อมกันไม่ได้หรอกเนาะ แต่ Spooling เอาดิสก์มาทำเป็นกล่องรับจดหมายหน้าห้อง ใครมีงานก็เอามาหยอดทิ้งไว้พร้อมกันได้ แล้วให้พรินต์เดมอนทยอยหยิบไปพิมพ์ โพรเซสเลยไม่ต้องแย่งสิทธิ์ผูกขาดเครื่องพิมพ์ตรงๆ อีกต่อไป

• กลไก ข) ทำลายเงื่อนไข: ถือและรอ (Hold and Wait)
  เหตุผล: เหมือนสั่งบุฟเฟต์ที่ต้องยกของมาวางเต็มโต๊ะก่อนถึงจะยอมหยิบช้อนกิน ถ้าขาดอะไรไปชิ้นเดียวก็ไม่เริ่ม จึงไม่มีจังหวะที่มือหนึ่งถือของชิ้นหนึ่งอยู่แล้วไปยืนต่อคิวรออีกชิ้นอย่างแน่นอน

• กลไก ค) ทำลายเงื่อนไข: ไม่มีการบังคับ / ไม่มีการริบทรัพยากร (No Preemption)
  เหตุผล: เมื่อไหร่ที่ขอของเพิ่มแล้วระบบไม่มีให้ ระบบจะกระชากของเดิมที่ถืออยู่กลับคืนเข้าส่วนกลางทันที (Forcefully Preempt) ไม่ปล่อยให้กอดของไว้รอแล้วขวางทางชาวบ้าน

• กลไก ง) ทำลายเงื่อนไข: การรอแบบวงกลม (Circular Wait)
  เหตุผล: ล็อกทิศทางเดียวเหมือนบันไดเลื่อนขาขึ้น ใครถือของเบอร์สูงจะถอยหลังไปขอเบอร์ต่ำไม่ได้ เส้นทางในกราฟเลยเป็นเส้นตรง ไม่มีทางวนกลับมาจูบก้นตัวเองเป็นวงกลมได้แน่นอน
1.2 เลือกกลไกมา 1 ข้อ แล้ววิเคราะห์ผลเสียด้านประสิทธิภาพการใช้ทรัพยากรที่เกิดขึ้นจากกลไกนั้น พร้อมยกตัวอย่างสถานการณ์ที่ทำให้เกิดการอดตาย (starvation) ได้
ตอบ: เลือกวิเคราะห์: กลไก ข) (การบังคับร้องขอทรัพยากรทั้งหมดในครั้งเดียวก่อนเริ่มทำงาน)
• ผลเสียด้านประสิทธิภาพการใช้ทรัพยากร:
  1. ทรัพยากรถูกดองเปล่าๆ โดยไม่ได้ใช้จริง: เช่น GPU อาจจำเป็นต้องใช้แค่ 10 วินาทีสุดท้ายตอนเรนเดอร์ผลลัพธ์ แต่ต้องจองกั๊กไว้ตั้งแต่เริ่มเปิดโปรแกรม ทำให้โพรเซสอื่นที่จำเป็นต้องใช้ตอนนั้นหมดสิทธิ์ใช้งาน เปลืองทรัพยากรจัดๆ
  2. ลดความคล่องตัวของระบบ: โพรเซสจำนวนมากต้องจอดแช่ที่สถานะพร้อม เพียงเพราะรออุปกรณ์เสริมชิ้นสุดท้ายชิ้นเดียว งานในระบบเลยไหลเวียนช้าลงอย่างเห็นได้ชัด

• ตัวอย่างสถานการณ์ที่ทำให้เกิดการอดตาย (Starvation):
  สมมติงานใหญ่ P ขอ CPU + RAM 16GB + GPU พร้อมกัน แต่ในระบบมีงานสั้นๆ ทยอยเข้ามาตลอดเวลา สลับกันจอง RAM บ้าง GPU บ้าง ทำให้ไม่มีจังหวะเวลาไหนเลยที่ทั้ง 3 อย่างจะว่างพร้อมกัน งานใหญ่เลยยืนแห้งคาคิวไปตลอดกาล เกิด Starvation ในที่สุด
1.3 เหตุใดเงื่อนไขสามข้อแรกจึงถือเป็น “เงื่อนไขจำเป็นแต่ยังไม่พอเพียง” ต่อการเกิดภาวะติดตาย จงอธิบายพร้อมยกตัวอย่างระบบที่ครบสามเงื่อนไขแรกแต่ไม่เกิดภาวะติดตาย
ตอบ: • เหตุผลที่เรียกว่า 'เงื่อนไขจำเป็นแต่ยังไม่พอเพียง':
  - จำเป็น (Necessary): ถ้าเกิด Deadlock ขึ้นมา แปลว่าต้องมี 3 ข้อแรกยืนพื้นแน่ๆ ขาดข้อใดข้อหนึ่งไม่มีทางเกิดเด็ดขาด
  - ยังไม่พอเพียง (Not Sufficient): ต่อให้มีครบทั้ง 3 ข้อ แต่ถ้าไม่มี 'การรอคอยแบบวงกลม' (Circular Wait) ตัวสุดท้ายที่ถือของอยู่ก็ทำงานจนเสร็จ แล้วปล่อยของคืนให้เพื่อนได้อยู่ดี ไม่ค้างหรอกเนาะ

• ตัวอย่างระบบที่ครบสามเงื่อนไขแรกแต่รอด ไม่เกิด Deadlock:
  สมมติมี 2 โพรเซสคือ P1 กับ P2 และมีทรัพยากร R1 (เครื่องพิมพ์ 1 เครื่อง) กับ R2 (สแกนเนอร์ 1 เครื่อง)
  1. Mutual Exclusion: ทั้ง R1 และ R2 ใช้งานได้ทีละตัว
  2. Hold and Wait: P1 ถือ R1 ไว้ และกำลังรอขอ R2
  3. No Preemption: ระบบไม่ริบ R1 จาก P1 คืน
  [สถานการณ์]: P2 ถือ R2 อยู่ แต่ P2 รันงานตัวเองไปเรื่อยๆ โดย 'ไม่ได้รอขอทรัพยากรใดเพิ่มเลย'
  ผลลัพธ์: ระบบไม่มีวงกลม (P2 ไม่ได้รอ P1) พอ P2 ทำงานเสร็จก็ปล่อย R2 คืนให้ระบบ P1 ก็หยิบ R2 ไปทำงานต่อจนจบ ทุกตัวรอดหมด ไร้ปัญหา Deadlock สิ้นเชิง
ข้อ 2. กราฟการจัดสรรทรัพยากร (Resource-Allocation Graph) (10 คะแนน)
กำหนดให้ระบบหนึ่งมีโพรเซส 4 ตัว คือ P1, P2, P3 และ P4 และมีทรัพยากร 3 ชนิด คือ R1 (1 หน่วย), R2 (2 หน่วย) และ R3 (1 หน่วย) โดยมีสถานะการถือครองและการร้องขอดังนี้
• การถือครอง (Assignment edge): R1 → P1, R2 → P2, R2 → P4, R3 → P3
• การร้องขอ (Request edge): P1 → R2, P2 → R3, P3 → R1
• โพรเซสที่ไม่ได้ร้องขอเพิ่ม: P4
2.1 จงวาดกราฟการจัดสรรทรัพยากรของระบบนี้ โดยใช้สัญลักษณ์ตามที่เรียนมา (วงกลมแทนโพรเซส สี่เหลี่ยมแทนทรัพยากร จุดภายในแทนจำนวนหน่วย)
ตอบ: กราฟการจัดสรรทรัพยากร (Resource-Allocation Graph) ของระบบแสดงดังแผนภาพด้านล่าง:
รูปที่ 1 แผนภาพ Resource-Allocation Graph สำหรับข้อ 2.1
2.2 ในกราฟที่วาดมีวงกลม (cycle) หรือไม่ ถ้ามี จงเขียนเส้นทางของวงกลมนั้นออกมาให้ครบทุกวง
ตอบ: ในกราฟที่วาดมี วงกลม (Cycle) เกิดขึ้นจำนวน 1 วง
เส้นทางของวงกลม (Cycle Path) คือ:
  P1 → R2 → P2 → R3 → P3 → R1 → P1
  (หรือมองผ่านทรัพยากร: R2 → P2 → R3 → P3 → R1 → P1 → R2)
หมายเหตุ: สำหรับเส้นทางที่ผ่าน P4 คือ R2 → P4 ไม่วนกลับเป็นวงกลม เพราะ P4 ไม่ได้ร้องขอทรัพยากรใดเพิ่ม
2.3 ระบบนี้เกิดภาวะติดตายหรือไม่ จงตอบพร้อมแสดงลำดับการทำงานของโพรเซสที่สนับสนุนคำตอบ และอธิบายว่าเหตุใดการมีวงกลมในกราฟจึงไม่ได้แปลว่าเกิดภาวะติดตายเสมอไป
ตอบ: ตอบ: ฟันธงเลยว่า 'ไม่เกิด Deadlock!'

• ลำดับการทำงานที่รอดจนจบ:
  1. P4 ถือ R2 อยู่ 1 ตัว และไม่ได้รอใคร P4 เลยรันต่อไปจนจบแบบชิลๆ
  2. พอ P4 รันเสร็จ ก็คืน R2 จำนวน 1 หน่วยกลับเข้ากองกลาง
  3. ระบบเอา R2 ที่เพิ่งได้คืนนี้ส่งต่อให้ P1 (เส้น P1 → R2 สำเร็จทันที)
  4. P1 ได้ของครบ รันจนเสร็จแล้วปล่อยทั้ง R1 และ R2 คืนระบบ
  5. P3 ได้รับ R1 ที่ว่างลง รันจนเสร็จแล้วคืน R1 กับ R3
  6. P2 ได้รับ R3 รันจนเสร็จเป็นตัวสุดท้าย
  ลำดับการรันที่ปลอดภัยคือ: P4 → P1 → P3 → P2 ทุกตัวรอดหมด

• ทำไมมีวงกลมแล้วถึงไม่เกิด Deadlock เสมอไป:
  ถ้าทรัพยากรมีแค่ 1 หน่วยเดี่ยวๆ (Single Instance) มีวงกลม = Deadlock 100% แน่นอน
  แต่ในข้อนี้ ทรัพยากร R2 มันมี 2 หน่วย โดยตัวหนึ่งถูกถือไว้โดย P4 ที่อยู่นอกวงรอบและไม่ได้รอใคร พอ P4 ทำงานเสร็จแล้วคืนทรัพยากรออกมา วงรอบการรอก็แตกสลายทันที ระบบจึงรอด
2.4 หากเพิ่มเส้นร้องขอ P4 → R3 เข้าไปในกราฟเดิม คำตอบในข้อ 2.3 จะเปลี่ยนไปหรือไม่ เพราะเหตุใด
ตอบ: ตอบ: เปลี่ยนแน่นอน คราวนี้กลายเป็น 'Deadlock 100%!'

เหตุผล:
1. พอเพิ่มเส้น P4 → R3 เข้ามา จะทำให้เกิดวงรอบใหม่อีกวงคือ: P4 → R3 → P3 → R1 → P1 → R2 → P4
2. R2 มี 2 หน่วยก็จริง แต่โดน P2 กับ P4 กอดไว้ทั้งคู่ ซึ่งตอนนี้ทั้งสองตัวต่างก็กำลังรอ R3
3. R3 ดันถูก P3 ถือไว้ และ P3 กำลังรอ R1 จาก P1
4. แล้ว P1 ก็กำลังรอ R2 จาก P2/P4 วนเป็นงูกินหางครบทั้งระบบ
5. ผลคือโพรเซสทุกตัวในระบบ (P1, P2, P3, P4) ติดล็อกกันเองอย่างสมบูรณ์ ไม่มีใครยอมใครและไม่มีใครรันจบได้เลย กลายเป็น Deadlock ถาวร
ข้อ 3. เกณฑ์การวิเคราะห์ประสิทธิภาพของการจัดลำดับ (10 คะแนน)
โพรเซส P มีประวัติการทำงานในระบบตามไทม์ไลน์ต่อไปนี้ (หน่วยเป็น ms)
• t = 3: เข้าสู่ระบบและเข้าคิวพร้อม
• t = 3 – 5: รออยู่ในคิวพร้อม
• t = 5 – 7: ได้ใช้หน่วยประมวลผลกลางครั้งที่ 1
• t = 7 – 13: รอการทำงานของอุปกรณ์นำเข้า-ส่งออก (I/O)
• t = 13 – 17: กลับมารออยู่ในคิวพร้อม
• t = 17 – 19: ได้ใช้หน่วยประมวลผลกลางครั้งที่ 2 แล้วทำงานเสร็จสิ้น
3.1 จงคำนวณค่า Turnaround Time, Waiting Time และ Response Time ของโพรเซส P พร้อมแสดงวิธีคิด และตรวจสอบว่าผลรวมของเวลาใช้ CPU เวลารอ I/O และเวลารอในคิวพร้อม สอดคล้องกับค่า Turnaround Time หรือไม่
ตอบ: คำนวณทีละตัวแบบเนื้อๆ ไม่ยืดเยื้อ:
1. Turnaround Time (TAT) = เวลาเสร็จ - เวลาเข้า = 19 - 3 = 16 ms
2. Waiting Time (WT) = รอรอบแรก (5 - 3 = 2) + รอรอบสอง (17 - 13 = 4) = 6 ms
3. Response Time (RT) = แตะ CPU ครั้งแรก (5) - เวลาเข้า (3) = 2 ms

4. ตรวจสอบความสอดคล้องของผลรวม:
   - เวลาใช้ CPU รวม = (7 - 5) + (19 - 17) = 2 + 2 = 4 ms
   - เวลาที่รอทำ I/O = 13 - 7 = 6 ms
   - เวลารอในคิวพร้อม = 6 ms
   ผลรวม = 4 + 6 + 6 = 16 ms
   ผลตรวจ: ได้ 16 ms ตรงกับ Turnaround Time เป๊ะอย่างสมบูรณ์
3.2 จงอธิบายความแตกต่างระหว่าง Waiting Time กับ Turnaround Time และเหตุใดเวลาที่รอ I/O จึงไม่ถูกนับเป็น Waiting Time ของการจัดลำดับหน่วยประมวลผลกลาง
ตอบ: • ความแตกต่าง:
  - Turnaround Time: เวลารวมตั้งแต่ก้าวเท้าเข้าระบบจนงานเสร็จออกจากระบบ รวมหมดทั้งรัน CPU, ทำ I/O, และยืนรอคิว
  - Waiting Time: นับเฉพาะเวลาที่ 'ตัวพร้อมรันแล้ว แต่ต้องยืนเฉยๆ ในคิวพร้อมเพราะ CPU ติดงานอื่น'

• ทำไมเวลารอ I/O ถึงไม่นับเป็น Waiting Time ของ CPU Scheduling:
  1. ตอนรอ I/O โพรเซสมันถูกย้ายไปนอนรอที่ Blocked State ต่อให้ CPU ว่าง โพรเซสก็ยังรันไม่ได้จนกว่าอุปกรณ์จะอ่านส่งข้อมูลเสร็จ
  2. เรากำลังวัดฝีมือของ CPU Scheduler ว่ากระจาย CPU ให้คนที่พร้อมทำงานได้ฉับไวแค่ไหน ความช้าของอุปกรณ์ I/O เป็นเรื่องของฮาร์ดแวร์ภายนอก จะเอามาโทษว่าเป็นความล่าช้าของ CPU Scheduler ไม่ได้หรอกเนาะ
3.3 จงยกตัวอย่างระบบงานจริงมา 2 ระบบ ระบบหนึ่งที่ควรออกแบบให้ Response Time ต่ำที่สุด และอีกระบบหนึ่งที่ควรออกแบบให้ Throughput สูงที่สุด พร้อมอธิบายว่าการปรับปรุงเกณฑ์หนึ่งอาจทำให้อีกเกณฑ์แย่ลงได้อย่างไร
ตอบ: • 2 ตัวอย่างระบบงานจริง:
  1. เน้น Response Time ต่ำสุด: เช่น UI มือถือ (iOS/Android), ตู้ ATM, ระบบจองตั๋วคอนเสิร์ต แตะปุ๊บต้องติดปั๊บ ดีเลย์นิดเดียวผู้ใช้หัวร้อนทันที
  2. เน้น Throughput สูงสุด: เช่น Render Farm ทำกราฟิกหนัง 3D, ระบบประมวลผลภาษีหรือคำนวณเงินเดือนสิ้นเดือน เน้นปั่นงานก้อนใหญ่ให้เสร็จเยอะที่สุดใน 1 วัน ไม่ต้องมาคอยโต้ตอบกับใคร

• การปรับปรุงเกณฑ์หนึ่งทำให้แย่อีกเกณฑ์ยังไง (Trade-off):
  - ถ้าอยากได้ Response Time ไวสุด: ต้องหั่นเวลา Quantum สั้นจิ๋ว สลับงานรัวๆ ผลคือเสียเวลาสลับ Context Switch บานเบอะ ซีพียูเอาเวลาไปโหลด/เซฟงานแทนที่จะทำงานจริง งานรวมเลยเสร็จช้า Throughput ตกฮวบ
  - ถ้าอยากได้ Throughput สูงสุด: ปล่อยงานรันยาวๆ แบบ FCFS ไม่ต้องสลับบ่อย ซีพียูปั่นงานเต็มสปีด แต่ถ้ามีงานด่วนของคนอื่นเข้ามา ก็ต้องยืนรอจนเหงือกแห้ง Response Time พังยับ
3.4 Dispatch Latency คืออะไร เกิดขึ้นในขั้นตอนใดของการเปลี่ยนโพรเซส และเหตุใดจึงถือเป็นค่าใช้จ่ายของระบบ (overhead)
ตอบ: • Dispatch Latency คือ: ค่าธรรมเนียมเวลาที่ตัวส่งงาน (Dispatcher) ต้องใช้ในการหยุดโพรเซสเก่า แล้วส่งมอบ CPU ให้โพรเซสใหม่เริ่มรัน

• เกิดขึ้นในขั้นตอน:
  1. สลับโหมดจาก User เป็น Kernel
  2. เซฟสถานะ (Context) ของโพรเซสเดิมลง PCB (พวก Register, PC, Stack Pointer)
  3. เลือกโพรเซสใหม่จาก Ready Queue
  4. โหลดสถานะของโพรเซสใหม่ขึ้นฮาร์ดแวร์
  5. ล้างแคช/สลับตารางหน่วยความจำ (TLB flush)
  6. สลับกลับเป็น User Mode แล้วสั่งลุยคำสั่งถัดไป

• ทำไมถึงถือเป็น Overhead:
  เพราะช่วงเวลานี้ CPU ไม่ได้ทำงานที่มีประโยชน์ให้ผู้ใช้เลยแม้แต่นิดเดียว เป็นเวลาที่ระบบปฏิบัติการเสียไปกับการจัดการตัวเอง ยิ่งสลับบ่อย ประสิทธิภาพจริงของเครื่องก็ยิ่งร่วง
ตอนที่ 2 ภาวะติดตาย: การคำนวณและวิเคราะห์ (2 ข้อ ข้อละ 15 คะแนน รวม 30 คะแนน)
ข้อ 1. อัลกอริทึมนายธนาคาร (Banker’s Algorithm) (15 คะแนน)
ระบบหนึ่งมีโพรเซส 5 ตัว คือ P0 ถึง P4 และมีทรัพยากร 3 ประเภท ได้แก่ A (10 หน่วย), B (6 หน่วย) และ C (8 หน่วย) ณ เวลา T0 มีสถานะการจัดสรรดังตาราง
1.1 จงคำนวณตาราง Need ให้ครบทุกโพรเซส และคำนวณเวกเตอร์ Available ณ เวลา T0 พร้อมแสดงวิธีคิด
ตอบ: 1. คำนวณ Need (สูตร: Need = Max - Allocation):
   - Need[P0] = (7, 4, 3) - (0, 1, 1) = (7, 3, 2)
   - Need[P1] = (3, 2, 2) - (2, 0, 2) = (1, 2, 0)
   - Need[P2] = (9, 1, 4) - (3, 1, 3) = (6, 0, 1)
   - Need[P3] = (4, 2, 2) - (2, 1, 1) = (2, 1, 1)
   - Need[P4] = (5, 3, 3) - (1, 1, 0) = (4, 2, 3)

2. คำนวณ Available ณ เวลา T0:
   - ยอดทรัพยากรที่แจกไปแล้ว = (0+2+3+2+1, 1+0+1+1+1, 1+2+3+1+0) = (8, 4, 7)
   - Available = ทรัพยากรทั้งหมด (10, 6, 8) - ยอดที่แจกไป (8, 4, 7) = (2, 2, 1)
1.2 จงใช้ Safety Algorithm ตรวจสอบว่าระบบอยู่ในสถานะที่ปลอดภัยหรือไม่ โดยแสดงค่า Work และ Finish ในทุกรอบการทำงาน และระบุลำดับที่ปลอดภัย (Safe Sequence) ที่ได้
ตอบ: ตรวจ Safety Algorithm ทีละรอบ:
• เริ่มต้น: Work = (2, 2, 1), Finish = [False ทั้งหมด]
• รอบที่ 1: P1 ต้องการ (1, 2, 0) ซึ่งพอกับ Work (2, 2, 1) -> P1 รันเสร็จ คืนของ Work กลายเป็น (2, 2, 1) + (2, 0, 2) = (4, 2, 3), Finish[P1] = True
• รอบที่ 2: P3 ต้องการ (2, 1, 1) ซึ่งพอกับ Work (4, 2, 3) -> P3 รันเสร็จ คืนของ Work กลายเป็น (4, 2, 3) + (2, 1, 1) = (6, 3, 4), Finish[P3] = True
• รอบที่ 3: P2 ต้องการ (6, 0, 1) ซึ่งพอกับ Work (6, 3, 4) -> P2 รันเสร็จ คืนของ Work กลายเป็น (6, 3, 4) + (3, 1, 3) = (9, 4, 7), Finish[P2] = True
• รอบที่ 4: P0 ต้องการ (7, 3, 2) ซึ่งพอกับ Work (9, 4, 7) -> P0 รันเสร็จ คืนของ Work กลายเป็น (9, 4, 7) + (0, 1, 1) = (9, 5, 8), Finish[P0] = True
• รอบที่ 5: P4 ต้องการ (4, 2, 3) ซึ่งพอกับ Work (9, 5, 8) -> P4 รันเสร็จ คืนของ Work กลายเป็น (9, 5, 8) + (1, 1, 0) = (10, 6, 8), Finish[P4] = True

• ฟันธงผลลัพธ์: Finish เป็น True ครบทุกตัว ระบบอยู่ใน 'สถานะปลอดภัย (Safe State)'
  ลำดับ Safe Sequence คือ: < P1, P3, P2, P0, P4 >
1.3 โพรเซส P2 ร้องขอทรัพยากรเพิ่ม Request = (1, 0, 1) จงใช้ Resource-Request Algorithm ตัดสินว่าระบบควรจัดสรรให้หรือไม่ โดยแสดงการตรวจสอบเงื่อนไขทุกขั้น สถานะสมมติหลังจัดสรร และผลการตรวจสอบความปลอดภัย
ตอบ: วิเคราะห์ตาม Resource-Request Algorithm:
1. เช็คสิทธิ์: ขอ (1, 0, 1) <= Need[P2] (6, 0, 1) ผ่าน ไม่ขอเกินเพดาน
2. เช็คของในมือ: ขอ (1, 0, 1) <= Available (2, 2, 1) ผ่าน มีของพอให้ยืม
3. แกล้งจัดสรรจำลองสถานะ: Available เหลือ (1, 2, 0), P2 ถือเพิ่มเป็น (4, 1, 4), Need[P2] ลดเหลือ (5, 0, 0)
4. ตรวจ Safety บนสถานะสมมติ:
   - Work เริ่มที่ (1, 2, 0) -> ปลดล็อก P1 ได้ (Work กลายเป็น 3, 2, 2)
   - ปลดล็อก P3 ได้ (Work กลายเป็น 5, 3, 3)
   - ปลดล็อก P2 ได้ (Work กลายเป็น 9, 4, 7)
   - ปลดล็อก P0 ได้ (Work กลายเป็น 9, 5, 8)
   - ปลดล็อก P4 ได้ (Work กลายเป็น 10, 6, 8) รอดหมด!

• การตัดสินใจ: ระบบ 'อนุมัติจัดสรรให้ P2 ทันที' เพราะปล่อยกู้ไปแล้วระบบยังรอดปลอดภัย
1.4 โพรเซส P0 ร้องขอทรัพยากรเพิ่ม Request = (0, 2, 0) จงตัดสินด้วยวิธีเดียวกัน พร้อมอธิบายว่าผลลัพธ์ต่างจากข้อ 1.3 อย่างไร และเหตุใดระบบจึงต้องปฏิเสธคำขอทั้งที่ทรัพยากรว่างเพียงพอ
ตอบ: วิเคราะห์ตาม Resource-Request Algorithm (เริ่มจาก T0 ใหม่):
1. เช็คสิทธิ์: (0, 2, 0) <= Need[P0] (7, 3, 2) ผ่าน
2. เช็คของในมือ: (0, 2, 0) <= Available (2, 2, 1) ผ่าน (มี B=2 ให้ยืมพอดี)
3. ลองแกล้งจัดสรร: Available จะเหลือ (2, 0, 1) ทรัพยากร B เกลี้ยงคลัง (เหลือ 0)
4. ตรวจ Safety: ส่องดู Need ทุกตัวในระบบ เทียบกับ Work (2, 0, 1) ปรากฏว่า 'ไม่มีใครในระบบรันต่อได้เลยแม้แต่ตัวเดียว!' ติดหล่มกันหมด ตกสู่ Unsafe State ทันที

• การตัดสินใจ: ระบบ 'ปฏิเสธคำขอ สั่งให้ P0 รอไปก่อน'

• ต่างจากข้อ 1.3 และทำไมต้องปฏิเสธทั้งที่ของว่างพอ:
  ในข้อ 1.3 ปล่อยกู้แล้วยังมีทางรอด แต่ในข้อ 1.4 ถ้าให้ P0 ยืม B ไปจนหมด จะไม่มีใคร (โดยเฉพาะ P1 และ P3) ทำงานจบได้เลย แบงก์ยอมเก็บทรัพยากรไว้ติดมือ ดีกว่าปล่อยกู้จนเสี่ยงเจ๊งทั้งระบบ นี่คือหัวใจของการหลีกเลี่ยง Deadlock ล่วงหน้า
1.5 โพรเซส P4 ร้องขอทรัพยากรเพิ่ม Request = (3, 2, 2) จงระบุว่าคำร้องขอนี้ถูกปฏิเสธที่ขั้นตอนใดของอัลกอริทึม และการถูกปฏิเสธในลักษณะนี้ต่างจากกรณีข้อ 1.4 อย่างไร
ตอบ: • ขั้นตอนที่ถูกเตะตก: ถูกปฏิเสธตั้งแต่ 'ขั้นตอนที่ 2 ของ Resource-Request Algorithm'
  เพราะคลัง Available มีของแค่ (2, 2, 1) แต่ P4 ดันขอ (3, 2, 2) ทรัพยากร A มีแค่ 2 แต่ขอ 3 ของจริงไม่มีให้ P4 เลยต้องจอดรอทันที ไม่ต้องเสียเวลาไปตรวจความปลอดภัยในด่าน 3 หรอกเนาะ

• ความต่างจากข้อ 1.4:
  - ข้อ 1.5: ปฏิเสธเพราะ 'ของขาดแคลนจริงทางกายภาพ' (Physical Shortage) ไม่มีของจะให้
  - ข้อ 1.4: ของในคลังมีพอแจก แต่ปฏิเสธในเชิงตรรกะความปลอดภัย (Safety Avoidance) เพราะคำนวณแล้วว่าให้ไปแล้วจะพากันตายหมู่
1.6 จงอธิบายว่าเหตุใดอัลกอริทึมนายธนาคารจึงนำไปใช้จริงได้ยากในระบบปฏิบัติการทั่วไป โดยอ้างอิงถึงข้อมูลที่อัลกอริทึมต้องการล่วงหน้าและความซับซ้อนเชิงเวลา
ตอบ: เหตุผลที่ Banker's เอาไปใช้จริงใน OS ทั่วไปได้ยากจัดๆ:
1. มโน Max Claim ล่วงหน้าไม่ได้: ในการใช้งานจริง โปรแกรมเมอร์ยังไม่รู้เลยว่าผู้ใช้จะกดเซฟไฟล์ขนาดเท่าไหร่ หรือเปิดกี่แท็บ จะให้ไประบุเพดานความต้องการสูงสุดล่วงหน้าได้อย่างไร แถมโพรเซสก็เกิดดับตลอดเวลา
2. กินแรงเครื่องมหาศาล (Time Complexity): ความซับซ้อนคือ O(m * n^2) ถ้าเครื่องกำลังรันอยู่ 2,000 โพรเซส แล้วทุกครั้งที่มี System Call ขอเปิดไฟล์หรือขอเมมโมรี ต้องมารันตรวจลูปนี้ตลอดเวลา ซีพียูคงค้างสนิท Overhead บานเบอะจนใช้งานจริงไม่ไหว
ข้อ 2. การตรวจหาภาวะติดตายและการกู้คืน (15 คะแนน)
ระบบหนึ่งมีโพรเซส 4 ตัว คือ P0 ถึง P3 และทรัพยากร 3 ประเภท คือ A, B และ C โดย Snapshot ณ เวลา T0 เป็นดังนี้
• P0: Allocation = (1, 0, 1), Request = (0, 1, 0)
• P1: Allocation = (1, 1, 0), Request = (1, 0, 1)
• P2: Allocation = (0, 1, 1), Request = (1, 0, 0)
• P3: Allocation = (1, 0, 2), Request = (0, 1, 0)
2.1 กรณีที่ Available = (0, 0, 1) จงใช้ Detection Algorithm ตรวจสอบระบบ โดยแสดงค่า Work และ Finish ในทุกรอบ แล้วระบุว่าเกิดภาวะติดตายหรือไม่ และมีโพรเซสใดบ้างที่อยู่ในภาวะติดตาย
ตอบ: ตรวจด้วย Deadlock Detection Algorithm:
• เริ่มต้น: Work = Available = (0, 0, 1), Finish = [False ทั้ง 4 ตัว]
• ส่องดู Request เทียบกับ Work (0, 0, 1):
  - P0 ต้องการ B=1 แต่ Work มีแค่ C -> รันไม่ได้
  - P1 ต้องการ A=1, C=1 -> รันไม่ได้
  - P2 ต้องการ A=1 -> รันไม่ได้
  - P3 ต้องการ B=1 -> รันไม่ได้
  ไม่มีโพรเซสไหนเลยที่ Request <= Work!

• ฟันธงผลลัพธ์: 'เกิด Deadlock ทั้งแผง!'
  โพรเซสที่ติดล็อกคือ: P0, P1, P2, P3 ครบทุกตัวในระบบ
2.2 กรณีที่ Available = (0, 1, 0) โดยที่ตาราง Allocation และ Request เหมือนเดิมทุกประการ จงตรวจสอบซ้ำด้วยวิธีเดียวกัน ระบุลำดับการทำงานที่เป็นไปได้ และสรุปว่าทรัพยากรว่างเพียง 1 หน่วยที่ต่างกันส่งผลต่อระบบอย่างไร
ตอบ: ตรวจเมื่อ Available = (0, 1, 0):
• รอบที่ 1: Work = (0, 1, 0) ปลดล็อก P0 ได้พอดี! รันเสร็จคืนของ Work กลายเป็น (1, 1, 1)
• รอบที่ 2: Work (1, 1, 1) ปลดล็อก P1 ได้! รันเสร็จคืนของ Work กลายเป็น (2, 2, 1)
• รอบที่ 3: Work (2, 2, 1) ปลดล็อก P2 ได้! รันเสร็จคืนของ Work กลายเป็น (2, 3, 2)
• รอบที่ 4: Work (2, 3, 2) ปลดล็อก P3 ได้สบายๆ รันเสร็จจบหมด

• ฟันธง: 'ไม่เกิด Deadlock!' ลำดับที่เป็นไปได้คือ: < P0, P1, P2, P3 >

• บทเรียนจากทรัพยากรต่างกันแค่ 1 หน่วย:
  ในข้อ 2.1 ของว่างคือ C ซึ่งไม่มีใครเอาไปใช้ปลดล็อกอะไรได้เลย แต่ในข้อ 2.2 เปลี่ยนมาว่างที่ B ซึ่ง B คือ 'จุดคอขวดวิกฤต (Critical Bottleneck)' ที่ทุกคนรอคอย แค่มี B มาให้ตัวเดียว ก็เกิดปฏิกิริยาลูกโซ่ปลดล็อกทั้งระบบจนรอดหมด
2.3 จากผลในข้อ 2.1 หากต้องกู้คืนระบบด้วยวิธียกเลิกโพรเซสทีละตัว จงเลือกโพรเซสที่ควรถูกยกเลิกเป็นตัวแรก พร้อมระบุเกณฑ์ที่ใช้ตัดสินใจอย่างน้อย 2 เกณฑ์ แล้วตรวจสอบด้วยอัลกอริทึมว่าหลังยกเลิกโพรเซสนั้นแล้วภาวะติดตายหมดไปหรือไม่
ตอบ: • เลือกเชือดใครดี (Victim Selection): เลือกยกเลิก 'โพรเซส P2'

• 2 เกณฑ์ในการเลือกเชือด:
  1. ถือของคอขวดที่ระบบต้องการ: ในข้อ 2.1 ระบบขาดแคลน B ตัวที่ถือ B มีแค่ P1 กับ P2 ถ้าไปฆ่า P0 หรือ P3 จะได้แค่ A กับ C ซึ่งไม่ช่วยอะไร ต้องเลือกฆ่าคนถือ B เท่านั้น
  2. เสียหายน้อยสุด (Minimize Cost): P2 ถือของรวมแค่ 2 ชิ้น (B=1, C=1) ขณะที่ P1 ถือของที่มีค่ามากกว่า การปิด P2 จึงสูญเสียงายย้อนหลังน้อยที่สุด

• ตรวจสอบหลังเชือด P2:
  - ระบบริบคืนของจาก P2 (0, 1, 1) ทำให้ Available ใหม่กลายเป็น (0, 0, 1) + (0, 1, 1) = (0, 1, 2)
  - P0 รันได้ (ได้ Work เป็น 1, 1, 3) -> P1 รันได้ต่อ (Work เป็น 2, 2, 3) -> P3 รันได้จนจบ
  - ผลลัพธ์: โพรเซสที่เหลือ {P0, P1, P3} รอดหมด 'Deadlock หายเกลี้ยง 100%'
2.4 จงเปรียบเทียบการกู้คืนแบบยกเลิกโพรเซส (Process Termination) กับแบบบังคับคืนทรัพยากร (Resource Preemption) ในประเด็นการเลือกเหยื่อ การถอยกลับ (Rollback) และความเสี่ยงต่อการอดตาย
ตอบ: เปรียบเทียบหมัดต่อหมัด:
1. การเลือกเหยื่อ (Victim Selection):
   - ยกเลิกโพรเซส: เลือกว่าจะ 'สั่งฆ่า/ปิดโปรแกรม' ตัวไหนทิ้ง โดยดูจากความสำคัญ งานที่รันไปแล้ว และของที่ถือ
   - ริบทรัพยากร: เลือกว่าจะ 'กระชากของชิ้นไหน' คืนมา โดยคำนวณต้นทุนการริบที่ต่ำที่สุดที่จะปลดล็อกระบบได้

2. การถอยกลับ (Rollback):
   - ยกเลิกโพรเซส: ง่ายแต่งานพัง สั่ง Abort ทิ้งทันที ไม่ต้องมีกลไกย้อนเวลา แต่ต้องมารันใหม่ตั้งแต่ศูนย์
   - ริบทรัพยากร: ยุ่งยากจัดๆ ต้องมีระบบ Checkpoint เซฟจุดย้อนเวลาไว้ เพื่อให้ถอยหลังกลับไปก่อนจังหวะได้ของ แล้วค่อยให้กลับมารันต่อตอนได้ของคืน

3. ความเสี่ยง Starvation (อดตาย):
   - ยกเลิกโพรเซส: เสี่ยงต่ำ เพราะตัวที่โดนฆ่าไปแล้ว พอกลับมาเกิดใหม่จะไปต่อคิวใหม่
   - ริบทรัพยากร: เสี่ยงสูงมาก ถ้าเกณฑ์เลือกเหยื่อมันฟิกซ์ โพรเซสเดิมที่ต้นทุนต่ำจะโดนไถของซ้ำแล้วซ้ำเล่าจนไม่ได้เกิดสักที (ต้องแก้ด้วยการบวกแต้มตามจำนวนครั้งที่เคยโดนริบ)
2.5 หากระบบนี้เกิดภาวะติดตายไม่บ่อยนัก (ประมาณปีละครั้ง) จงวิเคราะห์ว่าควรเลือกใช้แนวทางใดระหว่างการตรวจหาและกู้คืน กับการปล่อยผ่าน (Ignore) พร้อมให้เหตุผลเชิงค่าใช้จ่ายของระบบ
ตอบ: ตอบ: ฟันธงว่าต้องเลือก 'ปล่อยผ่าน (Ignore / Ostrich Algorithm)' แน่นอน!

เหตุผลเชิงต้นทุนและความคุ้มค่า:
1. Overhead ตรวจจับมันแพงเกินไป: ถ้าจะตรวจหาและกู้คืน OS ต้องคอยบันทึกสถานะและรัน Detection Algorithm วนไปตลอด 24 ชั่วโมง 365 วัน กินแรง CPU และแรมทั้งปี
2. เกิดปีละหน รีบูตเครื่องเอาง่ายกว่า: ในเมื่อ Deadlock เกิดแค่ปีละครั้ง พอค้างก็แค่ให้แอดมินกดรีสตาร์ตเครื่องใหม่ 2 นาทีก็จบ คุ้มกว่าการเอาพลังประมวลผลทั้งปีไปแลกมหาศาล ระบบปฏิบัติการจริงอย่าง Windows และ Linux จึงเลือกปล่อยเบลอด้วยวิธีนี้กันทั้งนั้น
ตอนที่ 3 การจัดลำดับการใช้หน่วยประมวลผลกลาง: การคำนวณ (2 ข้อ ข้อละ 15 คะแนน รวม 30 คะแนน)
ข้อ 1. เปรียบเทียบอัลกอริทึมการจัดลำดับ 4 แบบ (15 คะแนน)
กำหนดให้โพรเซส 5 ตัวเข้าสู่ระบบตามข้อมูลต่อไปนี้ (หน่วยเวลาเป็น ms):
• P1: Arrival Time = 0, Burst Time = 7
• P2: Arrival Time = 2, Burst Time = 4
• P3: Arrival Time = 4, Burst Time = 1
• P4: Arrival Time = 5, Burst Time = 4

1.4 อัลกอริทึม Round-Robin เมื่อ Quantum = 2 ms โดยกำหนดกติกาว่า เมื่อโพรเซสใช้ quantum ครบ ให้โพรเซสที่เพิ่งเข้าสู่ระบบ ณ เวลานั้นเข้าคิวก่อน แล้วจึงนำโพรเซสที่ถูกหยุดต่อท้ายคิว
ตอบ: • จำลองสถานะคิวอย่างละเอียดตามกติกา:
  - t=0: คิว=[P1] -> P1 รัน 0-2 (เหลือ 5)
  - t=2: P2 มาก่อน P1 ต่อท้าย -> คิว=[P2, P1] -> P2 รัน 2-4 (เหลือ 2)
  - t=4: P3 มาก่อน P2 ต่อท้าย -> คิว=[P1, P3, P2] -> P1 รัน 4-6 (เหลือ 3) (t=5 P4 มา)
  - t=6: คิว=[P3, P2, P4, P1] -> P3 รัน 6-7 (จบ!)
  - t=7: คิว=[P2, P4, P1] -> P2 รัน 7-9 (จบ!) (t=8 P5 มา -> คิว=[P4, P1, P5])
  - t=9: P4 รัน 9-11 -> คิว=[P1, P5, P4]
  - t=11: P1 รัน 11-13 -> คิว=[P5, P4, P1]
  - t=13: P5 รัน 13-15 -> คิว=[P4, P1, P5]
  - t=15: P4 รัน 15-17 (จบ!)
  - t=17: P1 รัน 17-18 (จบ!)
  - t=18: P5 รัน 18-19 (จบ!)
• Gantt Chart: | P1(0-2) | P2(2-4) | P1(4-6) | P3(6-7) | P2(7-9) | P4(9-11) | P1(11-13) | P5(13-15) | P4(15-17) | P1(17-18) | P5(18-19) |
• คำนวณรายตัว:
  - P1: CT = 18, TAT = 18, WT = 11
  - P2: CT = 9,  TAT = 7,  WT = 3
  - P3: CT = 7,  TAT = 3,  WT = 2
  - P4: CT = 17, TAT = 12, WT = 8
  - P5: CT = 19, TAT = 11, WT = 8

  - Average Turnaround Time = 51 / 5 = 10.20 ms
  - Average Waiting Time = 32 / 5 = 6.40 ms

1.5 จงสรุปผลลัพธ์ทั้งสี่วิธีลงในตารางเปรียบเทียบด้านล่าง แล้วระบุว่าวิธีใดให้ค่าเฉลี่ยเวลารอต่ำที่สุดและสูงที่สุด พร้อมอธิบายสาเหตุ
ตอบ: • เวลารอต่ำสุด: SRT (Preemptive) (เฉลี่ย 3.60 ms)
  สาเหตุ: เพราะมันแทรกแซงเตะงานยาวออกไป แล้วเอางานที่เหลือเวลาสั้นที่สุดมารันก่อนเสมอ งานสั้นเลยได้ออกจากระบบอย่างไว ลดเวลารอสะสมได้ดีที่สุดตามทฤษฎี

• เวลารอสูงที่สุด: Round-Robin (q = 2 ms) (เฉลี่ย 6.40 ms)
  สาเหตุ: การหั่น Quantum เล็กแค่ 2 ms ทำให้ทุกตัวโดนสลับคิวกันทำ งานสั้นโดนดึงไปสลับคิวกับงานยาว ทุกตัวเลยค้างในระบบจนเกือบจบ เวลารอเฉลี่ยเลยพุ่งสูงลิ่ว
1.6 จากผลการคำนวณของท่าน จงชี้ให้เห็นปรากฏการณ์ convoy effect ที่เกิดขึ้นในวิธีใดวิธีหนึ่ง โดยอ้างอิงตัวเลขเวลารอของโพรเซสที่ได้รับผลกระทบ
ตอบ: ตอบ: Convoy Effect เกิดขึ้นชัดเจนมากใน 'FCFS'

• ชี้แจงด้วยตัวเลข:
  P1 งานยาว 7 ms เข้ามาตอน t=0 และยึด CPU ยาวไปจนถึง t=7 ทำให้ P3 ซึ่งต้องการใช้ CPU แค่ 1 ms แท้ๆ และมาถึงตั้งแต่ t=4 ต้องยืนต่อคิวรอจนถึงเวลา t=11 ส่งผลให้ P3 มีเวลารอสูงถึง 7 ms (รอนานกว่าเวลาทำงานจริงตัวเองถึง 7 เท่า!)
  ภาพที่งานเล็กๆ หลายตัวต้องมาจอดแช่ติดอยู่หลังงานใหญ่งานเดียว เหมือนมอเตอร์ไซค์ขับตามหลังรถบรรทุกสิบล้อเลนเดียว คือภาพของ Convoy Effect แท้ๆ
1.7 หากเปลี่ยน Quantum ของ Round-Robin จาก 2 ms เป็น 8 ms ผลลัพธ์จะมีแนวโน้มใกล้เคียงกับอัลกอริทึมใด และจำนวนครั้งของการสลับบริบท (Context Switch) จะเปลี่ยนไปอย่างไร จงอธิบายพร้อมประมาณจำนวนครั้งของการสลับบริบทในทั้งสองกรณี
ตอบ: 1. แนวโน้มผลลัพธ์: จะเหมือนกับ 'FCFS 100% เป๊ะๆ'
   เพราะงานที่ยาวที่สุดในระบบคือ P1 (ใช้ 7 ms) ซึ่งไม่มีตัวไหนใช้เกินโควตา 8 ms เลย ทุกตัวจึงได้รันรวดเดียวจบโดยไม่โดนตัดเวลาแม้แต่ครั้งเดียว

2. การสลับ Context Switch:
   - Quantum = 2 ms: สลับงานรัวๆ ไปถึง 11 บล็อก เกิด Context Switch ราว 10 ครั้ง
   - Quantum = 8 ms: แต่ละตัวรันรอบเดียวจบ มีแค่ 5 บล็อก เกิด Context Switch เพียง 4 ครั้ง
   สรุป: ลดจำนวนครั้ง Context Switch ลงได้ถึง 60% ประหยัด Overhead ของ OS มหาศาล
ข้อ 2. การจัดลำดับตามความสำคัญ Aging และคิวหลายระดับ (15 คะแนน)
กำหนดให้โพรเซส 5 ตัวมีข้อมูลดังตาราง โดยตัวเลข Priority ที่น้อยกว่าหมายถึงความสำคัญสูงกว่า:
• P1: Arrival = 0, Burst = 6, Priority = 3
• P2: Arrival = 1, Burst = 4, Priority = 1
• P3: Arrival = 3, Burst = 5, Priority = 4
• P4: Arrival = 5, Burst = 2, Priority = 2
• P5: Arrival = 7, Burst = 3, Priority = 1
2.1 จงจัดลำดับด้วย Priority Scheduling แบบ Non-preemptive พร้อมเขียน Gantt Chart และคำนวณค่าเฉลี่ยของเวลารอ

• เวลารอรายตัว (WT = Start Time - Arrival Time):
  - P1: 0 - 0 = 0 ms
  - P2: 6 - 1 = 5 ms
  - P5: 10 - 7 = 3 ms
  - P4: 13 - 5 = 8 ms
  - P3: 15 - 3 = 12 ms

2.2 จงจัดลำดับด้วย Priority Scheduling แบบ Preemptive พร้อมเขียน Gantt Chart และคำนวณค่าเฉลี่ยของเวลารอ แล้วเปรียบเทียบกับผลในข้อ 2.1

  - P1: รอรอบที่โดนแทรก 10 - 1 = 9 ms

  - P4: 7 - 5 - 2 = 0 ms (มาถึงแล้วได้รันทันที)
  - P5: 10 - 7 - 3 = 0 ms (มาถึงแล้วได้รันทันที)

• เปรียบเทียบกับข้อ 2.1:
  แบบ Preemptive ทำเวลารอเฉลี่ยได้ดีกว่าชัดเจน (4.20 ms เทียบกับ 5.60 ms) เพราะตัวสำคัญสูงอย่าง P2, P4, P5 มาถึงแล้วได้แทรกคิวรันทันทีโดยไม่ต้องรอ P1 ให้จบ เวลารอของพวกตัวท็อปเลยกลายเป็น 0 ms หมด
รูปที่ 3 Gantt Charts เปรียบเทียบ Priority Scheduling ทั้ง 2 แบบ (ข้อ 2 ตอนที่ 3)
2.3 โพรเซสใดมีความเสี่ยงต่อการอดตาย (Starvation) มากที่สุด จงระบุพร้อมอ้างอิงค่าเวลารอที่คำนวณได้ และอธิบายว่าหากมีโพรเซสความสำคัญสูงทยอยเข้าระบบอย่างต่อเนื่อง จะเกิดอะไรขึ้นกับโพรเซสนั้น
ตอบ: • ตัวที่เสี่ยงอดตาย (Starvation) ที่สุด: โพรเซส P3
  อ้างอิงตัวเลข: P3 ความสำคัญต่ำสุดในรุ่น (Priority = 4) และมีเวลารอนานสุดถึง 12 ms

• ถ้ามีงานสำคัญสูงทยอยเข้ามาเรื่อยๆ จะเกิดอะไรขึ้น:
  งานใหม่ที่มี Priority 1, 2 หรือ 3 จะแย่งแซงหน้า P3 ไปตลอดเวลา P3 จะถูกดองลืมอยู่ใน Ready Queue ไปชั่วกัลปาวสาน ไม่เคยได้แตะ CPU สักวินาที เกิด Starvation อย่างถาวร
2.4 หากระบบใช้เทคนิค Aging โดยเพิ่มความสำคัญขึ้น 1 ระดับ (ค่าตัวเลขลดลง 1) ทุก ๆ 4 หน่วยเวลาที่โพรเซสรออยู่ในคิวพร้อม จงระบุว่าผลลัพธ์ในข้อ 2.2 จะเปลี่ยนแปลงที่จุดใดบ้าง (ระบุเวลาและโพรเซสที่ลำดับเปลี่ยน) และคำนวณเวลารอใหม่ของโพรเซสที่ได้รับผลกระทบ
ตอบ: วิเคราะห์ Aging (บวกแต้มทุก 4 ms):
1. P1 โดนเด้งออกมาตอน t=1 พอถึงเวลา t=5 P1 ยืนรอครบ 4 ms พอดีเป๊ะ! ระบบเลยปรับ Priority ของ P1 จาก 3 กลายเป็น 2
2. ณ เวลา t=5 นั้นเอง P4 เพิ่งก้าวเท้าเข้ามาด้วย Priority 2 เท่ากัน แต่ตามกฎ FCFS โพรเซสที่ยืนในคิวก่อน (P1) ย่อมได้สิทธิ์ก่อน P4!

• จุดที่ลำดับเปลี่ยน:
  ที่ t=5 โพรเซส P1 ได้สลับขึ้นมารันแทน P4!
  ไทม์ไลน์จะกลายเป็น: P1 รัน 5-7 -> t=7 P5 มาเตะ P1 ออก P5 รัน 7-10 -> t=10 P4 (ที่ได้ Aging เป็น 1) ได้รัน 10-12 -> P1 รันต่อ 12-15 -> P3 รัน 15-20

• เวลารอใหม่ของตัวที่ได้รับผลกระทบ:
  - P4: จากเดิมได้รันที่ t=5 กลายเป็นต้องรอไปถึง t=10 เวลารอใหม่ = 10 - 5 = 5 ms (รอนานขึ้น 5 ms)
  - P1: เวลารอรวมเท่าเดิมคือ 9 ms แต่ได้รับการแบ่งช่วงมารันเร็วขึ้น ช่วยลดความหน่วง
2.5 ระบบหนึ่งใช้การจัดคิวหลายระดับแบบเลื่อนชั้นได้ (Multilevel Feedback Queue) จำนวน 3 คิว ดังนี้
– คิวที่ 0: Round-Robin, Quantum = 8 ms (ความสำคัญสูงสุด)
– คิวที่ 1: Round-Robin, Quantum = 16 ms
– คิวที่ 2: FCFS (ความสำคัญต่ำสุด)
ให้งาน CPU-bound งานหนึ่งที่ต้องใช้หน่วยประมวลผลกลางรวม 30 ms เข้าสู่ระบบที่เวลา 0 โดยไม่มีงานอื่นในระบบ จงระบุว่างานนี้ถูกเลื่อนลงคิวใด ณ เวลาใดบ้าง และทำงานเสร็จสิ้นที่เวลาเท่าใด
จากนั้นอธิบายว่าหากมีงาน I/O-bound ที่ใช้ CPU ครั้งละ 2 ms เข้ามาที่เวลา 10 ms งานดังกล่าวจะได้เปรียบอย่างไร และเหตุใด MLFQ จึงเหมาะกับระบบแบบโต้ตอบ
ตอบ: 1. ไทม์ไลน์งาน CPU-bound (รวม 30 ms):
   - t=0: เริ่มรันในคิว 0 (Quantum 8 ms)
   - t=8: รันครบ 8 ms ยังไม่เสร็จ (เหลือ 22 ms) โดนปรับลดชั้นลง คิว 1 ทันที ณ เวลา t=8 ms
   - t=8 ถึง 24: รันต่อในคิว 1 (Quantum 16 ms) รวมรันไป 24 ms ยังไม่เสร็จ (เหลือ 6 ms) โดนลดชั้นลง คิว 2 ทันที ณ เวลา t=24 ms
   - t=24 ถึง 30: รันต่อในคิว 2 (FCFS) อีก 6 ms งานเสร็จสิ้นสมบูรณ์ ณ เวลา t=30 ms

2. งาน I/O-bound (ใช้ CPU ทีละ 2 ms) เข้ามาที่ t=10 ms ได้เปรียบอย่างไร:
   - ได้เข้าคิว 0 บนสุดเสมอ และสามารถแทรกแซง (Preempt) แย่ง CPU มาจากงานใหญ่ที่อยู่คิว 1 ได้ทันทีตอน t=10 ms
   - รันแค่ 2 ms ก็ปล่อย CPU ไปทำ I/O จึงไม่เคยใช้เวลาเกินโควตา 8 ms เลย ทำให้ตัวมันไม่เคยโดนลดชั้นลงคิวล่าง ได้อยู่คิวบนสุดตลอดไป

3. ทำไม MLFQ ถึงเหมาะกับระบบโต้ตอบ (Interactive Systems):
   เพราะงานโต้ตอบ (พิมพ์คีย์บอร์ด ขยับเมาส์) เป็นงาน I/O-bound สั้นๆ MLFQ จะยกมันขึ้นหิ้งไว้คิวบนสุดอัตโนมัติ ทำให้ผู้ใช้รู้สึกว่าระบบลื่นไหลตอบสนองทันใจ ส่วนงานคำนวณหนักๆ ก็ถูกผลักไปรันคิวล่างด้วย Quantum ก้อนใหญ่ ไม่เสียเวลาสลับ Context Switch บ่อย วิน-วินทั้งคู่
ตอนที่ 4 โจทย์ประยุกต์กับสถานการณ์จริง (1 ข้อ 10 คะแนน)
ข้อ 1. ระบบควบคุมหุ่นยนต์ขนของในคลังสินค้า (10 คะแนน)
คลังสินค้าอัตโนมัติแห่งหนึ่งมีหุ่นยนต์ขนของ (AGV) หลายคันทำงานพร้อมกันภายใต้ระบบปฏิบัติการเดียว หุ่นยนต์แต่ละคันต้องจองทรัพยากรที่ใช้ร่วมกัน 2 อย่างเพื่อส่งของให้สำเร็จ คือ ช่องทางเดินแคบ (มีเพียง 1 ช่อง) และ ลิฟต์ขนของ (มีเพียง 1 ตัว) โดยหุ่นยนต์คันที่ 1 จองช่องทางเดินก่อนแล้วจึงจองลิฟต์ ส่วนหุ่นยนต์คันที่ 2 จองลิฟต์ก่อนแล้วจึงจองช่องทางเดิน นอกจากนี้ระบบยังต้องประมวลผลงาน 3 ประเภทพร้อมกัน ได้แก่ งานควบคุมเบรกฉุกเฉิน (ต้องตอบสนองภายใน 5 ms เสมอ) งานอ่านค่าเซนเซอร์ทุก 50 ms และงานสรุปรายงานสิ้นวัน
1.1 จงอธิบายว่าภาวะติดตายเกิดขึ้นได้อย่างไรในสถานการณ์นี้ โดยระบุให้ครบทั้งสี่เงื่อนไขว่าแต่ละเงื่อนไขปรากฏอยู่ที่ส่วนใดของระบบ
ตอบ: Deadlock เกิดขึ้นเมื่อหุ่นยนต์สองคันต่างถือของคนละอย่างแล้วจอดรอของอีกอย่างพร้อมกัน ครบทั้ง 4 เงื่อนไขของ Coffman ดังนี้:
1. Mutual Exclusion (การไม่เกิดร่วม): อยู่ที่ 'ทางเดินแคบ (1 ช่อง)' กับ 'ลิฟต์ (1 ตัว)' หุ่นเข้าใช้งานได้ทีละคันเท่านั้น แชร์กันไม่ได้
2. Hold and Wait (ถือครองและรอคอย): หุ่น 1 ยึดทางเดินไว้แล้วจอดรอลิฟต์ ส่วนหุ่น 2 ยึดลิฟต์ไว้แล้วจอดรอทางเดิน กอดของไว้ไม่ยอมปล่อย
3. No Preemption (ไม่มีการแย่งชิง): ระบบความปลอดภัยไม่มีคำสั่งบังคับให้หุ่นคันไหนถอยหลังสละทางเดินหรือถอยออกจากลิฟต์กลางคัน
4. Circular Wait (รอคอยเป็นวงกลม): หุ่น 1 (ถือทางเดิน) รอลิฟต์จากหุ่น 2 และ หุ่น 2 (ถือลิฟต์) รอทางเดินจากหุ่น 1 จ้องหน้ากันนิ่งสนิท ขยับไม่ได้ตลอดกาล
1.2 จงเสนอวิธีป้องกัน (Prevention) 1 วิธี และวิธีหลีกเลี่ยง (Avoidance) 1 วิธี ที่นำไปใช้กับระบบนี้ได้จริง พร้อมระบุข้อดีและข้อเสียของแต่ละวิธีในบริบทของคลังสินค้า
ตอบ: 1. วิธีป้องกัน (Deadlock Prevention):
   • วิธีที่เสนอ: กำหนดลำดับการจองอย่างเด็ดขาด (Resource Ordering) ให้ทางเดิน = 1, ลิฟต์ = 2 บังคับว่าหุ่นทุกคันต้องจองทางเดินก่อน ถึงจะมีสิทธิ์จองลิฟต์ ห้ามจองลิฟต์ก่อนเด็ดขาด
   • ข้อดี: แก้ Circular Wait ได้เด็ดขาด 100% ไม่ต้องคำนวณอะไรซับซ้อน
   • ข้อเสีย: ขาดความยืดหยุ่น หุ่นที่อยู่หน้าลิฟต์ก็ต้องอ้อมไปจองทางเดินก่อน เกิดคอขวดที่ทางเดิน ขนของช้าลง

2. วิธีหลีกเลี่ยง (Deadlock Avoidance):
   • วิธีที่เสนอ: ใช้ Banker's Algorithm ผ่านเซิร์ฟเวอร์ส่วนกลาง ก่อนหุ่นจะขยับเข้าจอง ให้เซิร์ฟเวอร์จำลองดูก่อน ถ้าปล่อยไปแล้วมีแววติด Unsafe State สั่งให้หุ่นจอดรอที่ลานพักคอยภายนอกก่อน
   • ข้อดี: ยืดหยุ่นสูง หุ่นเลือกเส้นทางที่เร็วที่สุดของตัวเองได้ ทรัพยากรถูกใช้งานคุ้มค่า
   • ข้อเสีย: ต้องมีเน็ตเวิร์กและเซิร์ฟเวอร์คอยคำนวณแบบ Real-time ตลอดเวลา ถ้าหุ่นเยอะ Overhead จะสูง
1.3 ระบบควรเลือกใช้อัลกอริทึมการจัดลำดับแบบใดกับงานทั้ง 3 ประเภท จงออกแบบโครงสร้างคิวพร้อมระบุอัลกอริทึมของแต่ละคิว และอธิบายว่าควรกำหนด Quantum ขนาดใหญ่หรือเล็ก เพราะเหตุใด
ตอบ: • โครงสร้างคิว: ใช้ 'Multilevel Queue Scheduling แบบ Strict Fixed-Priority Preemptive' 3 ระดับ:
  - คิว 1 (สูงสุด): 'งานควบคุมเบรกฉุกเฉิน' — ใช้อัลกอริทึม Preemptive Priority ทันทีที่เซนเซอร์จับเจอคนเดินตัดหน้า ต้องสั่งเบรกทันทีภายใน 5 ms ห้ามรอใคร
  - คิว 2 (ปานกลาง): 'งานอ่านค่าเซนเซอร์ทุก 50 ms' — ใช้ Rate-Monotonic หรือ Round-Robin ทำงานตามคาบเวลาสม่ำเสมอ
  - คิว 3 (ต่ำสุด): 'งานสรุปรายงานสิ้นวัน' — ใช้ FCFS หรือ Round-Robin รันเป็น Background ตอนไม่มีงานด่วน

• ขนาด Quantum (ใหญ่หรือเล็ก เพราะเหตุใด):
  - งานเบรกฉุกเฉิน: ไม่ใช้ Quantum เลย แต่แทรกแซง (Preempt) สั่งหยุดทันที
  - งานรายงานสิ้นวัน: ใช้ 'Quantum ขนาดใหญ่ (เช่น 50-100 ms)' เพราะเป็นงานคำนวณข้อมูลปริมาณมาก การให้ก้อนเวลาใหญ่ช่วยลดการสลับ Context Switch ทำให้ CPU ปั่นงานเต็มสูบและเสร็จไวยิ่งขึ้น
1.4 Priority Inversion คืออะไร จงยกตัวอย่างลำดับเหตุการณ์ที่ทำให้งานควบคุมเบรกฉุกเฉินต้องรองานสรุปรายงานสิ้นวัน และเสนอวิธีแก้ปัญหาพร้อมอธิบายหลักการทำงานของวิธีนั้น
ตอบ: • Priority Inversion คือ: ปรากฏการณ์ที่งานสำคัญสูงสุด (High-priority) ดันต้องมานั่งรอคอยงานต่ำต้อย (Low-priority) ทางอ้อม เพราะมีงานระดับกลาง (Medium-priority) เข้ามาแย่งคิวแทรกแซง

• ตัวอย่างโศกนาฏกรรมเบรกแตกในคลังสินค้า:
  1. งานสรุปรายงานสิ้นวัน (L) กำลังทำงาน และได้ทำการล็อก Mutex เมมโมรีส่วนกลางไว้
  2. งานควบคุมเบรกฉุกเฉิน (H) ตรวจเจอคนตัดหน้า จึงจะเข้ามาสั่งหยุดล้อ แต่สั่งไม่ได้เพราะ Mutex ยังติดอยู่ที่งาน L ทำให้งาน H ต้องถูกบล็อกรอ
  3. ทันใดนั้น งานอ่านเซนเซอร์ (M) ถึงรอบ 50 ms พอดี เนื่องจาก M สำคัญกว่า L งาน M จึงเข้ามาแย่ง CPU จาก L ไปรันเฉยเลย!
  4. ผลลัพธ์: งาน L โดนดอง ไม่ได้ใช้ CPU เลยไม่มีโอกาสทำงานเสร็จเพื่อปล่อย Mutex งานเบรกฉุกเฉิน H ก็นั่งรอขาขวิดจนชนคนบาดเจ็บ!

• วิธีแก้: ใช้ 'Priority Inheritance Protocol (การสืบทอดความสำคัญ)'
  หลักการ: จังหวะที่งานสูงสุด H ต้องรอ Lock จากงานต่ำต้อย L ระบบปฏิบัติการจะเสกยศชั่วคราวให้งาน L มี Priority สูงเท่ากับ H ทันที! เพื่อป้องกันไม่ให้งานระดับกลาง M มาแย่ง CPU ไปได้ งาน L จะได้รีบทำส่วนที่ล็อกไว้ให้เสร็จแล้วคืน Lock ให้เบรกฉุกเฉิน H เข้ามารับช่วงต่อและสั่งเบรกได้ทันเวลา 5 ms รอดตายหวุดหวิด
